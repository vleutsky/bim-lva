32. [x] **Абсолютные координаты в сводке** — `COORDINATE_TO_ORIGIN` больше не
    включается для всех геодезических моделей (он сдвигал каждый файл к своему
    центру, и сводка схлопывалась в кучу). На заводской сетке (~1200 м) Tekla

    тесселяцию у нуля — положение возвращаем по точкам файла, а не просим
    «Выравнивание». Старый кэш геометрии со сбросом отбрасывается.
    Закреплено в `npm run smoke` и `npm run test-plant-grid`.
33. [x] **Карта-подложка (онлайн)** — OSM и космоснимок ESRI тайлами под
    моделью, плюс свой шаблон для MapTiler/Mapbox с ключом пользователя.
    Привязка одной точкой (координаты модели ↔ широта/долгота) + поворот,
    охват, прозрачность, драпировка на рельеф. Яндекс/Google/2ГИС не
    поддерживаются намеренно — их условия запрещают тайлы вне своего виджета.
    **Рельеф с карты** — отдельный меш высот в том же охвате и привязке
    (AWS Terrarium без ключа или Terrain-RGB со своим ключом, как подложка).
    **Площадка с карты** — окно-глобус как в InfraWorks: поиск места, слои
    (космоснимок ESRI, схема OSM, топо, отмывка), рамка
    или произвольный контур, лимит 200 га, кнопка «Загрузить» (космоснимок +
    рельеф). Точка открытия — Санкт-Петербург (59.93°N, 30.34°E). Повторное
    открытие после зума «весь мир» возвращает город (или последнюю площадку);
    поиск СПб и Москвы не зависит от Nominatim. После загрузки
    рельеф и подложка появляются в дереве («Площадка с карты»), оверлей
    «добавьте модели» скрывается, **лента черчения включается** (полилиния, ось
    трассы, поперечники, площадки, тело по оси, замер) — раньше из
    инструментов открывались только «Полилиния» и «Замер». На пустой сцене два режима посадки:
    **в нули** (центр рамки в (0, 0) плана, отметка Z с DEM) и **мировые
    координаты** (Гаусс–Крюгер 6° на WGS84, восток с номером зоны — не МСК
    площадки). Меш в мировых E/N, `ifcWorldOrigin` сдвигает группу к нулю
    сцены — статус-бар показывает настоящие метры. Если модель уже загружена,
    переключатель игнорируется — карта садится в координаты модели.
    Старый диалог привязки к модели — «Привязка к модели…».
    Подложка и «Рельеф, отмывка» остаются картинкой (`isGeoRaster`, луч их
    не сверлит); DEM — обычная поверхность, по ней работают профиль,
    поперечники и «откосы до рельефа». Если в сцене уже есть модель, сетка
    Terrarium сдвигается по Z на отметку модели (иначе у моря ~30 м, а в
    файле 141 м). Космоснимок не открылся — пробуем схему OSM. Шаг глобального DEM ~10–30 м: для
    «ось на карте → откосы» годится, для объёмов и посадки здания — нет
    (там LandXML / IFC / свой растр). Проверка — `npm run test-basemap`

36. [x] **Локомотив в туре** — «Проезд по трассе» и свободная езда WASD теперь
    ездят машиной или локомотивом на выбор. Модель процедурная (чужих ассетов
    нет), размеры настоящие: 22.0 м по автосцепкам, 3.10 ширины, крыша 4.60 от
    УГР, сложенный токоприёмник 4.99 — внутри габарита 1-Т по ГОСТ 9238; колея
    1520, две трёхосные тележки, колёса Ø1220. Камера сама отодвигается под
    длину состава. Габарит проверяется в `npm run smoke`

37. [x] **Метка XYZ** — кнопка 📍: клик по модели ставит точку и подпись с
    абсолютными X, Y, Z (метры). Точка перетаскивается по геометрии, подпись
    висит на полке (выноска + горизонтальная черта) и таскается отдельно.
    Кнопка 📋 открывает список меток: перелёт к метке, копирование тройки,
    удаление, выгрузка всех в буфер. Слой свой — «Очистить замеры» метки не
    трогает. Числа считаются тем же путём, что и строка состояния; smoke
    сверяет подпись с пересчётом и проверяет перетаскивание
38. [x] **Линейка 2D/3D/уклон** — режим замера «2D/3D/i»: по двум точкам сразу
    наклонное расстояние, горизонтальное проложение, превышение и уклон в ‰,
    % и 1:n, плюс катеты треугольника в сцене. Формула уклона вынесена
    отдельно и проверяется числами в `npm run smoke` (на плоской фикстуре
    клики её не задевают)

39. [x] **Обновить модель** — в контекстном меню дерева «⟳ Обновить модель» и
    «⟳ Обновить все»: файл перечитывается, камера и остальные модели остаются
    на месте. Где браузер даёт `FileSystemFileHandle` (перетаскивание в Chrome,
    `showOpenFilePicker`) — молча; иначе один диалог выбора файла вместо
    «удалить и добавить заново». Проверка в `npm run smoke`: старая версия
    уходит, дубля нет, соседние модели не задеты

40. [x] **Видовой куб** — в углу сцены кнопки «Верх / Низ / С / Ю / З / В /
    Изо». Стороны света стоят как на плане. Если что-то выделено, вид
    кадрируется по выделению. В `npm run smoke` сверяется вектор взгляда
    камеры для каждого из шести видов, а не факт нажатия
41. [x] **Черчение полилиний + экспорт DXF** — кнопка ✏ и переключатель 2D/3D:
    точки ложатся на геометрию (тот же луч, что и пикинг), 2D-линия держит
    отметку первой точки. Esc завершает линию. Кнопка ⤓ DXF выгружает все
    полилинии и метки XYZ в ASCII DXF R2010 (AC1024) с единицами «метры», слоями
    `2Д` / `3Д` / `Точки` и **мировыми** координатами — файл открывается
    в Civil 3D на своём месте. Полилинии пишутся как POLYLINE (не LWPOLYLINE).
    Файл — **UTF-8** (не Windows-1251): Civil 2010+ читает AC1024 как UTF-8,
    иначе падает «ошибка в таблице APPID» на первом кириллическом слое.
    У TABLE/записей есть owner `330`, у LAYER — `370`/`390` и `ACAD_PLOTSTYLENAME`.
    Содержимое DXF проверяется в `npm run smoke`

42. [x] **Ноль сцены помнит свои оси** — первая крупная модель задаёт общий ноль,
    но IFC приходит Y-up, а DXF/DWG/FBX — Z-up. Раньше пересчёт в абсолютные
    координаты выбирал формулу по тому, во что попал курсор: при промахе север
    и отметка менялись местами, у DWG уезжал север. Теперь система осей
    хранится вместе с нулём, пересчёт один на всех.
    Проверка — `npm run test-mixed-origin`

43. [x] **Ортогональная проекция** — кнопка «Персп / Орто» на видовом кубе.
    Камера подменяется целиком (OrbitControls, лучи, проекция подписей берут
    её из одной переменной), охват кадра при переключении сохраняется.
    Для планов и 2D-чертежей — обязательна. В `npm run smoke` проверяется не
    флаг, а что в орто по сцене по-прежнему можно попасть кликом

44. [x] **Объектная привязка** — кнопка ⊹ (включена по умолчанию): вершины,
    середины и точки на рёбрах. Работает и для черчения полилиний, и для
    замеров. Кандидат выбирается по расстоянию в **экранных пикселях**, поэтому
    порог не надо менять при зуме. Линии из DWG/DXF обрабатываются отдельно: у
    них нет грани, зато есть отрезок — привязка к концам осей нужна чаще всего.
    Под курсором показывается маркер: квадрат — вершина, треугольник —
    середина, круг — ребро. Проверка в `npm run smoke`

45. [x] **Сущности DWG/DXF поштучно** — линии, дуги, полилинии, грани и точки
    чертежа стали отдельными объектами: видны в дереве под своим слоем,
    выбираются кликом в сцене, подсвечиваются и показывают слой, тип, число
    вершин, длину и мировой центр. Геометрия при этом **осталась склеенной по
    слоям** — иначе на плане с десятками тысяч линий было бы столько же вызовов
    отрисовки; сущность опознаётся по диапазону вершин в общем буфере.
    В дереве показываются первые 500 на слой (больше DOM не выдержит),
    в сцене выбираются все. Проверки в `npm run smoke`: дерево, выбор поштучно,
    свойства и границы бинарного поиска по вершинам

46. [x] **Тело по оси** — кнопка ⬒: осью служит выбранная линия чертежа DWG/DXF
    или последняя начерченная полилиния, сечение задаётся размерами
    (прямоугольник, трапеция для канав и насыпей, круг, труба со стенкой) плюс
    смещение по высоте. Сечение ведётся параллельным переносом системы
    координат — на поворотах тело не перекручивается. В отчёте длина оси,
    площадь сечения и объём. Тела выгружаются в DXF одним 3DSOLID на слой
    `Тело`. Математика проверяется числами в `npm run smoke`: объём равен
    площади × длину, габарит совпадает с сечением, у трубы — площадь кольца

47. [x] **Как файл сел и переключатель на место** — в «Анализ → CRS» у каждого
    файла подписано, что с его координатами сделали: «вычтен общий ноль сцены»
    или красным «ПОСАЖЕН В СВОЙ ЦЕНТР — мировые координаты потеряны» (раньше
    это происходило молча, и модель просто оказывалась не там; теперь ещё и
    уведомление при загрузке). Рядом кнопка «⇲ Поставить по мировым
    координатам»: считает разницу между текущим положением и габаритом,
    снятым при загрузке, и возвращает файл на место. Проверка в
    `npm run test-geo-seq`: модель нарочно сдвигают и возвращают — остаток 0.000 м

48. [x] **Цепочка размещения IFC** — в «Диагностике IFC» кнопка «🔗 Цепочка
    размещения»: второй проход по файлу строит индекс всех IfcLocalPlacement /
    IfcAxis2Placement3D / IfcCartesianPoint / IfcDirection, находит IfcSite и
    один типовой элемент, и печатает координаты на КАЖДОМ шаге цепочки
    PlacementRelTo — от элемента до корня, плюс отдельно резолвит
    `IfcGeometricRepresentationContext.WorldCoordinateSystem` (мировой сдвиг
    может лежать и там, вне цепочки размещения — так подтвердилось на реальном
    файле АР). Каждый пропуск отмечен явно («не нашлось» — RelativePlacement=$
    или дырка в индексе), а не тихо заменён нулём — иначе не отличить «файл так
    написан» от «мой парсер не справился». Проверено фикстурами: оторванный
    элемент (`PlacementRelTo=$`) и площадка на identity-размещении с реальным
    сдвигом только в WCS

49. [x] **Автокоррекция WorldCoordinateSystem** — если IFC привезён с ODA
    (Renga, nanoCAD) и мировой сдвиг лежит не в цепочке `IfcLocalPlacement`, а
    в `IfcGeometricRepresentationContext.WorldCoordinateSystem`, вьювер находит
    его и применяет сам: разбирает начало файла, строит матрицу коррекции в
    осях фрагментов через ту же матрицу, что разворачивает сцену, и сдвигает
    геометрию перед вычитанием общего нуля. Срабатывает только когда похоже на
    именно этот случай — `IfcMapConversion` нет и геометрия ещё в локальном
    нуле, — иначе нормально геопривязанный файл получил бы двойной сдвиг.
    Найдено и подтверждено на реальном файле кнопкой «🔗 Цепочка размещения» в
    «Диагностике IFC» (см. п. 48). Проверено в `npm run test-rotated`.
    Поворот у ODA-экспорта иногда лежит не в `RefDirection` самого
    `WorldCoordinateSystem`, а в `TrueNorth` контекста (направление истинного
    севера относительно оси Y модели) — вьювер читает и его как запасной
    источник угла, формула другая (`atan2(Tx, Ty)`, а не `atan2(Ty, Tx)`).
    Подтверждено владельцем на реальном файле АР («Село как родное»).
50. [x] **Выбрать подобные** — в контекстном меню сцены (ПКМ по элементу)
    пункт «🧲 Выбрать подобные»: для IFC — тот же класс во всех загруженных
    моделях федерации, для DXF/DWG — та же сущность (линия/полилиния/дуга/…)
    на том же слое в пределах файла. Проверено в `npm run smoke` (оба пути).
51. [x] **Список полилиний + радиусы сопряжения** — кнопка «📐 Полилинии» в
    «Создать 2Д/3Д»: таблица начерченных полилиний (переименование, длина,
    приближение камерой, удаление), «✎» раскрывает точки — координаты
    (абсолютные, только просмотр), удаление отдельной вершины и радиус
    сопряжения в любой внутренней вершине (не в первой/последней) — та же
    операция, что «вписать радиус» в вершину трассы в Civil 3D. Радиус
    заменяет угол дугой (касательная `R/tan(α/2)`, центр на биссектрисе);
    касательные до исходной вершины остаются на экране пунктиром и потоньше —
    в DXF их нет, это только подсказка, откуда выросла дуга;
    если отрезки короче, чем нужно для радиуса, он усекается автоматически
    с уведомлением. Экспорт в DXF — тем же путём, что и прямые полилинии:
    дуга уходит частой ломаной (`buildDxf` не знает о дугах отдельно, ему
    все точки одинаковы). Проверено в `npm run smoke`: подсчёт точек и длины
    после сопряжения, переименование и общее удаление через список;
    после радиуса в сцене есть пунктирные тангенсы до вершины.

53. [x] **Полилинии: правка, замыкание, профиль, картограмма** — большой блок
    поверх пп. 51–52.
    - **Ручки вершин** в сцене: у раскрытой полилинии показываются маркеры,
      их тянут мышью (луч + привязка, как при черчении). Раньше подсказка
      обещала это, а кода не было — X/Y не правились никак.
    - **Замкнутый контур** (кнопка ⭘): углами становятся все вершины, включая
      крайние; считается площадь в плане; в DXF уходит флагом, а не повторной
      вершиной.
    - **Вставка вершины** (⊕ в строке) и **продолжение** полилинии с любого
      конца через контекстное меню — имя, цвет, толщина и радиусы сохраняются.
    - **Ввод числами** при черчении: длина, азимут (по часовой от севера) и
      превышение; пустой азимут продолжает прежним направлением, Enter ставит
      точку.
    - **Фильтр привязки**: галочки вершина/середина/ребро, выбор запоминается.
    - **Дуги в DXF**: сопряжение 2D-полилинии уходит настоящей дугой через
      bulge (код 42). У 3D bulge в R12 нет — там осталась ломаная, и это
      честно возвращается в `arcs: false`.
    - **Продольный профиль по оси** (〰): отметки земли лучом вниз, пикетаж,
      рабочие отметки, CSV, «посадить ось на землю». Промах луча даёт разрыв и
      прочерк, а не подставленный ноль.
    - **Картограмма** (⛰) по замкнутому контуру: метод квадратов, выемка,
      насыпь, баланс, диапазон рабочих отметок. Площадь считается по ячейкам с
      найденной землёй — только она соответствует посчитанному объёму.
    Проверено в `npm run smoke` числами: перетаскивание сдвигает вершину,
    площадь контура сходится с формулой шнурков, bulge — с `tan(Δ/4)` вместе

    отметки на Δ меняет баланс картограммы ровно на «площадь × Δ».

54. [x] **Откосы до рельефа** (кнопка «△ Откосы» в списке полилиний) — от
    каждой точки линии откос идёт по нормали в плане (влево / вправо / в обе
    стороны) до пересечения с рельефом: выше земли на бровке — насыпь (1:m,
    умолчание 1.5), ниже — выемка (1:m, умолчание 1). На выходе: поверхность
    откоса в сцене (раскраска по насыпи/выемке), линия выхода на землю —
    отдельной редактируемой полилинией на сцене (в DXF площадки не дублируется
    рёбрами: уходит один 3DSOLID; у замкнутой бровки линия выхода
    на сцене тоже замкнута; у разомкнутой бровки «в обе стороны»
    дополнительно строится замкнутый контур выхода через торцы), и
    объёмы насыпи/выемки по методу средних площадей. Целевая поверхность —
    уже построенные откосы и площадки, иначе исходный рельеф (проектная
    поверхность важнее рельефа даже когда она ниже: иначе сосед не видел бы
    выемку). Внутрь своей замкнутой площадки откос не идёт. Где поверхность
    не найдена или откос не дотянулся за максимальный вылет — сечение
    выпадает из площади, линии и объёма (не подставляем нули), а не роняет
    весь расчёт; на вогнутых углах соседние сечения могут налезть друг на
    друга — честно не вычищается.
    Проверено в `npm run smoke` числами (`createPolylineFromPoints` +
    `buildSlopeOnPolyline`): на ровной площадке экзит-дистанция и площадь
    сечения сходятся с аналитической формулой `d = m·(z_бровки − z_земли)`,
    а объём — с «площадь × длина» для случая насыпи и выемки по отдельности;
    отдельно проверено, что маленький максимальный вылет честно даёт
    пропущенные сечения и нулевой объём, а не подставленное число;
    выход на чужую площадку и на чужой откос сходится с аналитикой
    (две параллельные бровки, зазор 4 м → встреча при d=2 м);
    верхняя площадка, выходя на нижнюю, обходит её углы (вершины кольца в
    веере угла), а не режет хордой по диагонали;
    поверхность выемки рисуется поверх рельефа (`depthTest: false`), иначе
    откос уходит под исходную землю и видны только контуры;
    «в обе стороны» на замкнутом контуре внутрь даёт `own-pad`, наружу — d=H·m.
    Где бровка пересекает землю (насыпь сменяется выемкой), на ребре ставится
    шарнир: поверхность и линия выхода приходят на бровку в точке пересечения
    с землёй, линия выемки начинается от неё, а не от угла площадки.
    На замкнутом контуре шарнир на ребре «последняя→нулевая» не выкидывается.
    Проверено в `npm run smoke`: бровка с g+2 → g−2, шарнир в середине,
    линия выемки проходит через него и не сидит на угле; квадрат с выемкой
    на вершине 0 — линия выемки идёт от обоих шарниров, не от угла.
    У замкнутого контура середина заполняется как площадка (ear clipping в
    плане — иначе в TIN дыра до исходного рельефа): заливка рисуется поверх
    рельефа (`depthTest: false`, renderOrder 50, на 8 см выше бровки — в TIN
    отметки исходные), цвет площадки задаётся отдельно от цвета откоса и
    меняется без перестроения. У разомкнутой линии
    торцы закрываются откосом вдоль оси. Готовый TIN выгружается в Civil 3D:
    DXF R2010 слоем `Откос` — **один 3DSOLID на площадку** (ACIS SAT 700,
    открытый TIN — оболочка, замкнутый лофт КДО — тело), без 3D-полилиний
    по бровке и линии выхода; и LandXML 1.2 Surface (`Pnts`/`Faces`, northing
    easting elev — тот же формат, который вьювер сам читает). Проверено в
    `npm run smoke`: квадрат 4×4 даёт ровно 2 треугольника середины, заливка
    без depth-test и своего цвета, линия выхода на сцене замкнута (кодировка
    флагом 70=9, без повторной вершины), LandXML точка 1 совпадает с TIN,

    Таблица площадок (кнопка «▣ Площадки»): имя, цвет, площадь в плане,
    объёмы, выгрузка DXF/LandXML по строке; имя и цвет правятся без
    перестроения. Проверено в `npm run smoke`: строка квадрата 4×4, цвет

    Удаление линии выхода не вычёркивает соседнюю полилинию из списка
    (иначе контур остаётся на сцене, а в таблице пусто).

56. [x] **Поперечники по оси дороги** (кнопка **«🛣 Ось трассы»** на ленте
    «Черчение» и «Рельеф»; **«⊟ Поперечники»** там же; также «⊟» в списке

    **одна секущая по биссектрисе** (кромки сходятся уголком, miter
    `1/cos(δ/2)`), а не два перпендикуляра соседних звеньев; шаговые пикеты

    не считает. Земля снимается лучом вниз; промах — разрыв, не ноль.

    поперечник»**: одно окно, план сверху, профиль под ним, поперечник справа

    resolved ΔZ 0.2 при базе 0; формы покрытия и бордюра разного fill;
    сдвиг формы CURB не двигает кромку R и не меняет габарит 0.15×0.15;
    после сдвига бордюр не на R, возврат на 0.5 м примагничивает обратно;
    удаление CURB уносит CURBT;
    снятие галочки «откосы» убирает лучи с чертежа;
    линия земли на сечении доходит до края шаблона (бордюр) и до выхода
    откоса на рельеф, а не обрывается на ширине покрытия;
    при черчении ось пунктир, кромки сплошные; цвет/толщина
    кромок доходят до материала.
    **План как 3D:** кружки на всех вершинах оси (тянуть XY, Alt+клик —
    удалить, двойной клик по оси — вставить, Shift+клик на угле — прямой /
    скругление). Кромки тянутся курсором — ширина влево/вправо. На переломе
    оси выбор «прямой» (miter) или «скругление» (дуга, как веер площадки).
    Синие сечения в сцене лежат на отметке оси/шаблона, не на земле.
    Новая дорога: **3.25 м влево и 3.25 м вправо** (полоса). Проверено:
    поля ширины 3.25 до открытия окна; `designZ` совпадает с `axisSceneZ`,
    не с землёй; `planMoveVertex` двигает PI; `setRoadWidths` пишет 4.5/5;
    L-угол `fillet` 5 м → `radii[1] > 0`, `miter` → 0.
    На **узком скруглении** (плечо короче R, ширина больше вписанного радиуса)
    внутреннюю кромку не выворачивает за центр дуги: смещение внутрь режется
    радиусом кривизны, вырожденные грани полотна отбрасываются. Проверено:
    L 4+4 м, R=8, ширина 3.25 — `roadOffsetTravel` без обратного хода кромки.
    **Шаг поперечников** на прямых и на кривых раздельный (`шаг прям.` /
    `крив.`): на прямой 20 м, на сопряжении 5 м — меньше сечений, чем шаг 5 м
    по всей оси. Проверено: 80 м прямая + R=12 на 90°; на прямой шаг ≈20 м,
    сечений меньше, чем при шаге 4 м везде.
    **Слои 3D замкнутые:** лофт отбрасывает только вырожденные треугольники
    в 3D (длина нормали), а не нулевую площадь в плане — иначе бока одежды
    и торцы сечения пропадали, и формы выглядели открытыми листами.
    **Подписи плана и профиля** (HTML поверх SVG, клик — поле ввода): на плане
    длина звена, угол поворота Δ° и радиус (в т.ч. `R —`); на профиле **отметка
    у вершины** (красное, клик или клик по кружку) и «длина · уклон» в середине
    звена. Таблица профиля **выше ~136 px** и тянется ручкой `#rsSplitProfileTable`.
    Проверено: полотно ≥20 граней;
    L-угол показывает Δ90° и две длины; `editPolyline(..., 'defl', …)` крутит
    исходящее звено.
    Высоты плана, профиля и поперечника **не едут за размером палитры/окна**
    (после первого кадра фиксируются в пикселях). Вертикаль меняет только

## Дорожная карта: «Лего» из дорожных объектов

Цель владельца (18.08.2026), формулировка его: собирать дорогу, площадку,
парковку, зоны — как из кубиков, чтобы всё было 3D-телами и выгружалось в DWG.

Что для этого уже есть и на что опираться:

- **Тела и их сборка.** Коридор по оси, откосы до рельефа, слои КДО, площадки,
  узлы дорог — всё уже строится телами по одной схеме: шаблон поперечника →
  лофт между станциями (`corridorLoftPush`) → замкнутая оболочка. Новые
  «кубики» разумно делать этой же машинкой, а не заводить второй движок.
- **Стыковка кубиков** — самая ценная и самая недооценённая часть. Узел дорог
  уже показал, из чего она состоит: обрезать соседа (разрыв пикетажа), закрыть
  торец, протянуть внешний профиль по стыку, не посчитать объём дважды. Для
  парковки и зон понадобится то же самое, но между площадкой и дорогой.
- **Чего пока нет:** общего понятия «объект» с параметрами и связями (сейчас
  это разные массивы — `roadXsModels`, `slopeModels`, `roadIntersections`), и
  дерева этих объектов в интерфейсе.

**Про DWG — расхождение снято проверкой (19.08.2026).** Запись «DWG не пишем»
была неверна: она осталась от времён, когда единственным движком был `dwgdxf`
(только DWG→DXF). `@node-projects/acad-ts` (MIT) умеет писать, и это проверено
сквозняком, а не по описанию пакета: отрезок (10,20,0)→(110,20,0) записан в DWG
и прочитан обратно независимым `dwgdxf` — координаты совпали, сущность на месте
(AC1018 7787 б, AC1024 8808 б, AC1032 8776 б, сигнатуры верные). Нужные нам
сущности writer знает, включая `Solid3D`.
Что остаётся сделать для настоящей выгрузки: наш конвейер строит DXF **строками**,
а acad-ts работает через объектную модель — под DWG её придётся собирать заново.
И отдельно проверить на живом AutoCAD/Civil версии выше AC1018: они пишутся
раскладкой секций от R2004, хотя помечены своей версией. Подробности и грабли —
в §9 CLAUDE.md.
