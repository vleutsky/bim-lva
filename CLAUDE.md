## 3. Сборка плагинов: VS Code, без Visual Studio

Владелец работает **в VS Code**, не в Visual Studio. Solution `LVA.BIM.slnx`
открывать нечем — собираем из терминала `dotnet` CLI (проекты SDK-style,
это штатный путь, а не обходной).

```powershell
dotnet build LVA.Civil.BIM\LVA.Civil.BIM.csproj -c Release
```

- TFM выбирается по установленным Civil: 2022–2024 → `net48` (`Libs\2022`),
  2025+ → `net8.0-windows` (`Libs\2026`). Нет Civil на машине — оба.
  Явно: `-p:CivilTfms=net48`, всегда оба: `-p:CivilDetect=false`.
- Сборка **сама разворачивает** бандл в
  `%APPDATA%\Autodesk\ApplicationPlugins\LVA.BIM.bundle`. Если Civil держит DLL —
  `-p:SkipBundleDeploy=true`.
- `net48` требует MSBuild из Build Tools; `net8.0-windows` собирается одним .NET SDK.
- Расширение: **C# Dev Kit** (в `.vscode/settings.json` уже
  `"dotnet.preferCSharpExtension": true`). `.vscode/tasks.json` содержит задачи
  `build`/`publish`/`watch`, но они нацелены на `LVA.Tests`, а не на плагин.
- Inventor **не в solution** — собирается отдельно своим csproj.
- Тесты: `dotnet run --project LVA.Tests` (140 проверок, без AutoCAD).
- DLL подписываются сертификатом «LVA Code Signing» (`Tools\Sign-LvaDll.ps1`),
  пропуск — `-p:SkipSign=true`.

## 4. Лицензии — контракт (единственный источник правды)

Формат придуман **не нами**: он уже реализован в
`LVA.BIM.Common\Licensing\` (`LicenseGate.cs`, `LicenseModels.cs`) и в
`Tools\New-LvaLicense.ps1`. Веб подстроен под него. **Ничего здесь не менять,
не сверившись с C#.**

- Алгоритм: **RSA-SHA256, PKCS#1 v1.5** (не Ed25519 — была такая ошибка).
- Продукты: ровно `Civil`, `Navis`, `Inventor`, `*`. Других нет.
- Привязка к железу: `HostLock` = SHA-256 от
  `Win32_ComputerSystemProduct.UUID` (Trim → UpperInvariant → UTF8 → hex X2),
  64 hex-знака. Клиент получает его через `Tools\Get-LvaMachineId.ps1`.
- Каноническая строка:
  `LicenseId|ClientName|Products(через запятую)|IssuedUtc|ExpiresUtc|HostLock`
  Бессрочная — пустая строка в позиции `ExpiresUtc`, не `null`.
- **Даты — .NET `ToString("o")`: семь знаков дробной части.** JS `toISOString()`
  даёт три, и подпись не сходится после разбора JSON в C#. Для этого есть
  `toDotNetRoundTrip()`; на это завязана половина `npm run test-license`.
- Файл `license.lic` = JSON `{ Payload, Signature }`.
- **Бессрочная лицензия в UI:** `expires_at = null` нельзя гонять через
  `new Date(null)` — выйдет 1970 год и статус «Истекла». Офлайн-скрипт без
  `-ExpiresUtc` выдаёт именно бессрочные, так что после импорта это видно сразу.
  Оба места в `cabinet.html` (список получателя и таблица админа) прикрыты, за
  этим следит `npm run test-license-import`.

Ключи:

- Ключ подписи **кода** («LVA Code Signing») остаётся офлайн, в облако не уезжает.
- Для веба — **отдельная** пара: `tools/New-LvaWebKey.ps1` (RSA-3072,
  `New-SelfSignedCertificate`; на PS 5.1 нужен openssl из Git for Windows).
  Приватная часть → секрет `LICENSE_SIGNING_KEY` в Supabase, `pubkey-web.cer` →
  в `LVA.BIM.Common\Licensing\` и пересборка. `LicenseGate.VerifySignature`
  перебирает **все** встроенные `.cer`, поэтому старые лицензии не ломаются.
- Приватный ключ генерируется **только на машине владельца**. В чат, в репозиторий
  и в коммиты он не попадает никогда. `license-keys/` в `.gitignore`.
- Статический сайт — **не защищённое место**. Генератор ключей в браузере
  опубликовал бы секрет. Выпуск живёт только в Edge Function под `service_role`.
- `adminEmails` в `auth-config.js` — удобство UI, **не** защита. Права решает
  таблица `license_admins`.

## 9. Грабли (уже наступали)

- **Не выдумывать состав продукта.** Список плагинов, кнопок и продуктов брать
  из кода `LvaBim`. Дважды придумывался несуществующий перечень — оба раза мимо.
- **Не проектировать поверх непрочитанного.** Схема лицензий была построена с
  нуля (Ed25519, привязка к email+организации), хотя в репозитории уже работала
  своя — RSA и node-lock. Переделывать пришлось целиком.
- `tools/New-LvaWebKey.ps1` без UTF-8 BOM ломался на Windows PowerShell 5.1:
  без BOM файл читается в системной кодировке (у владельца — cp1251), кириллица
  в комментариях и строках превращается в крякозябры, и часть из них случайно
  складывается в символы вроде `"`/`}` — парсер валится на «непредвиденный
  токен» в местах, весьма далёких от настоящей причины. PS 7 эту же кодировку
  угадывает верно и без BOM — поэтому в песочнице (нет PS 5.1) баг не ловился.
  Чинится добавлением BOM (`\xef\xbb\xbf` первыми байтами файла) — дальше и
  PS 5.1, и PS 7 читают его как UTF-8 одинаково. Если появятся другие `.ps1` в
  этом репозитории — сразу с BOM, не постфактум.
- Тот же скрипт: уборка временных файлов в `finally` (`Remove-Item $pfx/$pem/...`)
  роняла **весь** запуск на Windows PowerShell 5.1 из-за глобального
  `$ErrorActionPreference = 'Stop'` — если `Remove-Item` не мог удалить файл
  (на профиле владельца путь пользователя с точкой в имени даёт короткое
  8.3-имя, `Test-Path` и `Remove-Item` иногда расходятся на таких путях), это
  превращалось в завершающую ошибку и обрывало скрипт **после** того, как
  приватный ключ уже был посчитан, но **до** записи `private-key.b64` на диск —
  то есть вся работа терялась на последнем шаге. Починка: `Remove-Item ...
  -ErrorAction SilentlyContinue` — уборка теперь best-effort и не может
  утопить уже готовый результат.
- Уточнение к грабле выше: `-ErrorAction SilentlyContinue` не спасал — эта
  конкретная ошибка `Remove-Item` кидается как `PSArgumentException` уже на
  этапе проверки аргумента, а не как обычная non-terminating ошибка cmdlet'а,
  и `-ErrorAction` её не гасит. Работает только `try { ... } catch { }` вокруг
  вызова целиком.
- `licenses.js`: `client()` была синхронной, а `auth.getSupabaseClient()`
  (`ensureSupabase` в `auth.js`) — асинхронная (догружает SDK с CDN). `client()`
  тихо возвращала сам `Promise`, и `client().auth` / `.from` / `.functions`
  падали с «Cannot read properties of undefined» — весь личный кабинет и
  admin-панель лицензий были нерабочими с самого начала. `npm run test-license`
  этого не ловит: проверяет только формат подписи, не браузерный код. Раз
  `getSupabaseClient()` асинхронная — любой её вызов в новом коде тоже надо
  `await`ить, синхронных обёрток вокруг нее не заводить.
- Не завышать эффект в коммитах и в отчётах: писать измеренное число.
  (Коллизии — 5.2 с, а не «минуты»; блоки DXF — +26 % сущностей, а не «половина
  чертежа».)
- `git cherry-pick -q` такого флага не имеет; неудачный `checkout` оставил не на

  скопировал: `RefDirection`=(cos α, sin α) даёт локальную ось X, поэтому
  угол — `atan2(y, x)`. `TrueNorth`=(Tx, Ty) — это направление истинного
  севера ОТНОСИТЕЛЬНО оси Y модели, поэтому угол, выравнивающий его с мировой
  осью Y — `atan2(Tx, Ty)` (компоненты в обратном порядке). Вывод через
  матрицу поворота: `R(θ)·(Tx,Ty) = (0,1)` разрешается в `θ = atan2(Tx,Ty)` —
  расписано в комментарии у `readWorldCoordinateSystemShift`. Числа сошлись
  сами по себе (не подгонял): `atan2(-0.20894, 0.97793) = -12.060°` — то же

  Revit или что-либо ещё подписывает углы в интерфейсе; UI-соглашения о знаке

  `worldOriginIfcVec()` отдают ноль в нужных осях; пересчёт координат один на
  всех и от попадания курсора не зависит. Закреплено в
  `npm run test-mixed-origin` (оба порядка загрузки DXF+IFC).
- **«Модель села не туда» — сначала сверить габариты, а не чинить origin.**
  Вьювер вычитает из **всех** файлов один и тот же вектор (`ifcWorldOrigin`,
  первая крупная модель), это чистый перенос — поссорить модели между собой он
  не может. Значит расхождение приехало из самих файлов. Проверка: «Анализ →
  CRS» показывает мировой габарит каждого файла (снимается до вычитания нуля),
  сверяется с Civil 3D «Свойства поверхности → Статистика»; тот же отчёт по
  отдельному файлу даёт «Диагностика IFC» в кабинете. Попытка «держать одно
  решение `COORDINATE_TO_ORIGIN` на всю федерацию» была сделана и откачена —
  это лечение симптома вслепую.
  Ещё: две отметки Z с разных скриншотов сравнивать бесполезно, если курсор
  стоял в разных точках — на уклоне пара метров набегает честно. Сравнивать
  надо min/max.
- **НАЙДЕНО И ПОЧИНЕНО: сводка на ЗАВОДСКОЙ сетке (~1200 м) разъезжалась.**
  Файлы из Tekla (АС и КМ, координаты общие и согласованные, в Navisworks
  садятся нормально) во вьювере разлетались на километр. Две причины,
  складывались:
  1. `LARGE_COORD_THRESHOLD` = 5000 м. Заводская сетка под него не проходит →
     файл не привязывается к общему нулю → `forceCenterFragmentsNearOrigin`
     сажает КАЖДЫЙ файл в свой центр, и взаимное положение уничтожается.
     Точность тут ни при чём: на 1200 м шаг float32 ≈ 0.14 мм. Починка —
     отдельная константа `SELF_CENTER_MAX_COORD` = 200 м: ниже неё модель
     считаем «выгруженной в своём нуле» (её и центрируем, как раньше), выше —
     координаты осмысленные и трогать их нельзя.
  2. `snapSceneContentToOrigin()` записывает свой сдвиг ТОЛЬКО в
     `ifcWorldOrigin`. Нуля нет — записать некуда: уже загруженные модели
     уезжают в ноль, а следующий файл приходит со своими настоящими
     координатами и оказывается за километр (замерено: 1608 м вместо 116.7).
     Починка — без нуля не двигаем ничего.
  ⚠️ Правка №1 сначала была сделана по порогу 5000 м и **уронила smoke**:
  фикстура `smoke-grid.ifc` (центр ≈ 80 м) перестала центрироваться, а тесты
  откосов чертят полилинии по фиксированным X/Y и промахнулись мимо модели
  («no-ground»). Отсюда и взялась отдельная константа 200 м.
  Закреплено в `npm run test-plant-grid` (числа из реальных файлов: IfcSite
  1242.0/1148.5 и 1194.6/1055.5). Проверять надо РАЗНОС между моделями:
  абсолютных координат мало, сцена законно до-центрируется и уводит обе.
- **НАЙДЕНА И ПОЧИНЕНА настоящая причина «файлы Tekla разъезжаются».**
  Приём разбора, который сработал: владелец намерил во вьювере 1708.94 м
  между двумя файлами, а в Navisworks — 116.15 м. Центр АС по Navisworks
  1231.43/1171.43/61.80, его модуль ≈ 1700.7 м — совпало с намеренным. Раз
  расстояние между моделями равно расстоянию от нуля до одной из них, значит
  вторая сидит В НУЛЕ, а не «немного уехала». Числа для сверки берутся из
  Navisworks: «Преобразовать центр» в свойствах файла даёт центр модели в
  мировых координатах. Добил показ габарита ДО вычитания нуля сцены («Анализ →
  CRS»): у КМ он оказался коробкой 18×12×7 м вокруг нуля — то есть координаты
  потеряны ЕЩЁ ДО координатного конвейера вьювера, их обнулил сам web-ifc.
  Две причины, обе починены:
  1. **`countIfcBooleanOps` не считал `IFCBOOLEANCLIPPINGRESULT`** —
     регулярка была `/IFCBOOLEANRESULT\s*\(/`, а `IFCBOOLEANCLIPPINGRESULT`
     это ОТДЕЛЬНЫЙ тип и под неё не подходит. У Tekla именно он и составляет
     почти все вырезы (в файле АС: 1613 clipping из 1997 булевых). Счёт
     занижался в разы, а от него зависят и `USE_FAST_BOOLS`, и решение о
     сбросе координат. Из-за этой же дыры первая версия теста НЕ воспроизвела
     поломку (`cto=false`) и чуть не увела в сторону.
  2. **Порог правила Tekla в `shouldForceCoordinateToOrigin` был 50 м:**
     `isTekla && isIfc2x3 && booleans >= 8 && worldMeters >= 50`. Под него
     попадает ЛЮБАЯ выгрузка промплощадки (координаты ~1200 м), и файл
     открывался с `COORDINATE_TO_ORIGIN` — координаты терялись безвозвратно.
     Поднят до `LARGE_COORD_THRESHOLD`: на 1200 м шаг float32 = 0.14 мм,
     жертвовать координатами ради точности CSG не за чем. Если геометрия
     всё-таки выйдет пустой, загрузка сама переоткроет файл с CTO (повтор уже
     есть в коде) — по факту, а не по догадке.
  Закреплено в `npm run test-plant-grid`: фикстуры воспроизводят выгрузку
  Tekla (IFC2X3, мм, 1997 и 294 выреза, центры из Navisworks). До правки
  тест давал ошибку 1699 м и `ПОСАЖЕН В СВОЙ ЦЕНТР` — ровно симптом владельца.
  `BimLvaDebug.modelAbsExtents[].cto` показывает, открыт ли файл со сбросом.
  Предупреждение о сбросе теперь срабатывает от `SELF_CENTER_MAX_COORD`
  (200 м), а не от 5000 м — на заводской сетке вьювер об этом МОЛЧАЛ.
  **Уточнение (КМ ~1195 м, 397 вырезов):** упреждающий CTO на 1200 м уже
  выключен, но файл всё равно мог открыться «со сбросом»: (1) кэш геометрии
  сохранял старые `openSettings.COORDINATE_TO_ORIGIN=true` и подсовывал
  меши у нуля; (2) повтор при пустой тесселяции всё ещё включал CTO и
  оставлял модель у нуля — GetCoordinationMatrix нули, вернуть сдвиг
  web-ifc не умеет. Починка: кэш со сбросом, если политика уже другая,
  отбрасываем; после CTO сажаем фрагменты по крупным `IFCCARTESIANPOINT`
  файла (Z-up → Y-up web-ifc). Предупреждение «Поставьте Выравниванием»
  только если восстановить не вышло.
- **`COORDINATE_TO_ORIGIN` ломает сводку.** web-ifc сдвигает им *каждый* файл к
  его собственному центру и не сообщает, на сколько (`GetCoordinationMatrix`
  возвращает нули — проверено). Включённый «для всех геодезических моделей», он
  схлопывал шесть файлов одной дороги в кучу у нуля; габариты при этом
  правильные, поэтому по ним поломка не видна. Включать только против float32-
  тесселяции CSG (много boolean). Без CSG вершины локальны, а мировое
  положение живёт в `flatTransformation` (double) — точность цела.
  Закреплено проверкой `checkGeoFederation` в `npm run smoke`.
- Схемы IFC4X1/IFC4X2 (Civil 3D, OpenRoads) web-ifc парсит нормально, хотя
  официально не заявляет: DATA-секция читается без оглядки на `FILE_SCHEMA`.
  Открываем их с предупреждением, а не отказом.
- **Карта-подложка: Яндекс/Google/2ГИС нельзя** — не технически, а по лицензии:
  их условия разрешают показывать карту только внутри их виджета, а нам нужна
  картинка текстурой под 3D. Bing Microsoft сворачивает в пользу Azure Maps.
  Остаются OSM (с оглядкой на их tile usage policy), спутник ESRI и свой
  шаблон MapTiler/Mapbox с ключом **пользователя** (в HTML ключ класть нельзя).
- Тайл-серверы из песочницы **закрыты прокси** (OSM, ESRI, Яндекс — все FAIL,
  npm при этом отвечает). Поэтому `npm run test-basemap` мокает тайлы через
  `page.route` и проверяет математику, а не сеть.
- **Меркатор ≠ метры.** Проекция растягивает всё в 1/cos(широты) раз (для 55.7°
  это 1.77×). Наивное «метр в метр» даёт правдоподобную, но целиком смещённую
  подложку. Поэтому UV подложки считается через `uvFor`: точка модели →
  широта/долгота → пиксель Меркатора. Линейный UV дал бы в центре ровно
  (0.5, 0.5) — на этом и построена проверка в тесте.
- Границы георастра — в **абсолютных** координатах (easting/northing), сдвиг
  нуля сцены компенсирует позиция `geoRasterGroup`. Поэтому драпировка и высота
  требуют поправки `worldShift`, иначе луч уходит за тысячи километров, а
  плоскость всплывает на высоту origin.
- Оси: web-ifc отдаёт геометрию в **Y-up** (E, h, −N), `globalGroup.rotation.x
  = π/2` разворачивает её в сцену **Z-up** (E, N, h). `ifcWorldOrigin` хранится
  в Y-up-системе — отсюда `currentWorldShiftEN()`.
- **Текстовый индекс IFC ленивый, и `ifcIndex` больше НЕ признак «это IFC».**
  Раньше наличие `ifcIndex` играло две роли сразу: сам индекс и флаг
  «модель редактируется» (35 проверок из 48). Сделать его ленивым, не разведя
  роли, нельзя — экспорт, фильтр классов, ведомость и объединение молча
  решили бы, что IFC не редактируется. Теперь: `canEditIfc(mod)` —
  синхронный признак (есть индекс ИЛИ есть файл), `hasIfcIndex(mod)` —
  «уже построен», `ensureIfcIndex(mod)` — асинхронное построение по запросу.
  Любая новая операция, читающая STEP-текст, обязана сначала
  `await ensureIfcIndex(...)` (или `ensureIfcIndexes` для всех моделей).
- **Кэш геометрии: в кэш идёт СЫРОЙ вывод `StreamAllMeshes`, а не готовая
  сцена.** Соблазн сложить вершины в абсолютные координаты и не хранить
  матрицы вставки силён (кэш стал бы меньше и проще), но на геодезической
  модели (55 300 м) float32 даёт шаг ≈4 мм — кэш сам бы двигал модель, ровно
  та же ловушка, из-за которой `COORDINATE_TO_ORIGIN` включается только против
  float32-CSG. Поэтому в записи локальные вершины (float32, как их отдал
  web-ifc) и матрица отдельно (float64), а весь конвейер после потока
  (единицы → WorldCoordinateSystem → ноль сцены) на кэшированном пути
  выполняется заново: он зависит от того, какие модели уже открыты, и «запечь»
  его значило бы посадить файл относительно случайного соседа по прошлой
  сводке. Закреплено в `npm run test-geom-cache` на геодезической фикстуре —
  на фикстуре у нуля потеря точности не видна вовсе.
- **Что кэш даёт по времени — мерить фазу геометрии, а не всё открытие.**
  Замер на сетке 20 000 коробок: сама фаза геометрии 464 → 104 мс (4.5×), а
  всё открытие 2743 → 2034 мс (1.35×). Разница потому, что старт страницы,
  инициализация WASM, `OpenModel`, батчинг, BVH и дерево остаются как были.
  Смотреть «стало ли быстрее» по общему времени — верный способ решить, что
  кэш бесполезен. Для этого в консоль печатается строка
  `геометрия из кэша|тесселирована за N мс`, а в тестах есть
  `BimLvaDebug.geomCache.phaseMs(файл)`.
- **Тест кэша нельзя синхронизировать по `modelBounds`.** Габариты появляются
  РАНЬШЕ, чем загрузка доходит до записи кэша, и проверка «первое открытие
  заполнило кэш» падала на пустой базе, хотя запись потом проходила. Конец
  загрузки — включение `#clear` в хвосте `loadFilesSequentially` (та же
  грабля, что с кнопками при массовой загрузке).
- **Замер памяти в V8: временные массивы утекают в результат.** Первый вариант
  бенчмарка индекса выдавал ОТРИЦАТЕЛЬНУЮ стоимость — сборщик убирал массив
  кусков текста уже после базовой отметки. Строить данные надо в функции,
  чтобы временное гарантированно исчезло до замера, и мерить каждую схему
  в своём процессе с `--expose-gc` и двойным `gc()`.
  Числа (730 000 сущностей): старая схема (массив строк + объекты) 83.7 МБ,
  новая (смещения в Int32Array) 28.0 МБ. На реальном файле АР владелец
  намерил старую в 64.2 МБ — плюс ~82 МБ текста, который она удерживала.
- **`split()` в V8 не копирует текст, а делает срезы на исходную строку.**
  Поэтому массив строк удерживает весь файл целиком, и отпустить его нельзя,
  пока жив хоть один элемент. Измерено: после освобождения исходной строки
  не освобождается ничего. Отсюда и переход на смещения.
- **Толщину линии в WebGL обычной `THREE.Line` задать нельзя.** `linewidth` у
  `LineBasicMaterial` молча игнорируется почти везде — это ограничение WebGL,
  не three. Поэтому начерченные полилиний — `Line2` + `LineGeometry` +
  `LineMaterial` (вендорится, см. `THREE_ADDONS` в `tools/vendor.mjs`). Цена:
  у `Line2` НЕТ атрибута `position` — позиции лежат в `instanceStart`/
  `instanceEnd`, поэтому всё, что читало геометрию линии напрямую, надо
  переводить на свой список точек (`record.renderPts`); на этом уже
  спотыкался `sweepAxisPoints()`. Ещё `LineMaterial` держит разрешение
  холста в пикселях — его надо обновлять в `resize()`, иначе толщина
  разъезжается при смене размера окна.
- **Выбор линии кликом сделан своим пикингом, а не `Line2.raycast`.** У Line2
  raycast экранный и зависит от `material.resolution` и от `linewidth`
  (порог = `linewidth + threshold`), то есть область попадания растёт вместе с
  толщиной линии. Вместо него — проекция `renderPts` через `projectToPixels()`
  и порог в **пикселях** (`POLYLINE_PICK_PX`), как у объектной привязки:
  предсказуемо и не зависит от стиля линии.
  ⚠️ При отладке пикинга по линии: точка клика и вершина полилинии **не
  совпадают** — объектная привязка уводит поставленную точку на ближайшую
  вершину геометрии (до ~12 px). Целиться надо в спроецированные вершины
  (`BimLvaDebug.polylineScreenPts`), иначе кажется, что пикинг сломан. На это
  уже потрачено время впустую.
- **Промах луча вниз — это не ноль и не «низ сцены».** В профиле по оси и в
  картограмме за краем поверхности отметки просто НЕТ. Маркером промаха служит
  `-Infinity`, переданный в `sampleTerrainZ` как fallback: сравнивать с обычным
  числом нельзя — оно может совпасть с настоящей отметкой. Такие пикеты дают
  разрыв линии и прочерк в таблице, а их число печатается. Подставить туда
  число значило бы соврать в чертеже.
- Площадь в картограмме считается по ячейкам с **найденной** землёй
  (`measured`), а не по всем внутри контура: только она соответствует
  посчитанному объёму. Иначе «объём / площадь» врал бы там, где часть контура
  висит над пустотой. На этом же построен точный тест: подъём проектной
  отметки на Δ обязан изменить баланс ровно на `площадь × Δ`.
- Азимут в вводе точки числами — геодезический: **по часовой от севера**,
  поэтому `dx = L·sin(A)`, `dy = L·cos(A)`, а не наоборот. Оси сцены Z-up:
  X — восток, Y — север. В тесте это ловится шагами на 90° и 0°.
- Таблица вершин полилинии перебирает `pts` (реальные вершины), а **не** `abs`:
  после сопряжения в `abs` лежат ещё и точки дуг, и нумерация строк разъедется
  с `radii`. На этом уже попадался — строки таблицы указывали не на те вершины.
- **Догрузка файла пересобирает меши — и стирала назначенный цвет.** Добавление
  файла зовёт до-центрирование сцены, оно двигает вершины и вызывает
  `rebuildIfcMeshesFromFragments()`. Батчи (`buildIfcBatches`) цвет из
  `appearanceByID` читали, а `addIndividualIfcMeshes()` — нет, и строила
  материалы из исходных цветов фрагментов. То есть у моделей МЕНЬШЕ порога
  батчинга (2000 фрагментов) покраска слетала при каждом добавлении файла.
  Теперь `addIndividualIfcMeshes` в конце возвращает сохранённое оформление.
- **Камеру вписываем только на ПЕРВОЙ загрузке.** `fitView()` стоял после
  каждой пачки, и добавление файла уводило пользователя с того места, куда он
  сам отзумился. Флаг `sceneWasEmpty` снимается в начале
  `loadFilesSequentially`. Проверять это через `cameraTarget` бесполезно:
  сцена до-центрируется, и цель остаётся у нуля в обоих случаях — сверять надо
  `cameraPos`.
- **Подсветка выделения оставалась навсегда на покрашенных элементах.** Снятие
  выделения идёт через `setEmissive(mesh, 0)` → `reapplyAppearanceForItem()`.
  Там две ветки: без оформления — `restoreMeshOriginalAppearance()`, она
  emissive гасила; с оформлением — `applyAppearanceToMesh()`, а она его не
  трогала вовсе. Теперь гасит и она, а `applyAppearanceToSelection()` возвращает
  подсветку тем, кто ещё выделен. После «Применить оформление» выделение
  снимается: под подсветкой назначенный цвет всё равно не разглядеть.
- **Не перестраивать таблицу, пока в ней набирают.** Профиль перерисовывается
  из десятка мест, и каждая перерисовка подменяла поле ввода новым — введённое
  пропадало на месте, а клик по полю вообще сбрасывал значение (обработчик
  подсветки строки перерисовывал таблицу прямо на клике). `renderProfileTable`
  теперь пропускает пересборку, если фокус внутри таблицы, а клик по
  `input/select/textarea` не считается выбором строки.
- **Профиль по оси показывает ВЕРШИНЫ, а не пикеты с шагом.** Шаг пикета
  убран из панели: промежуточные точки на прямой между вершинами ничего не
  сообщают, а таблицу раздувают до сотен строк. Земля при этом по-прежнему
  опрашивается часто (шаг = длина/400, подбирается сам) — иначе синяя линия
  срезала бы складки рельефа. То есть два разных ряда: густой для отрисовки
  земли и по вершинам для таблицы и правки.
- Пикет вершины меряется вдоль **renderPts** (с дугами), а сами вершины берутся
  из **pts** — иначе номера строк разъедутся с вершинами, как уже было в
  таблице полилинии. Вставка по пикету поэтому идёт в два шага: точка на
  renderPts → `nearestPolylineSegment()` → вставка между pts.
- `preserveAspectRatio="none"` у SVG профиля растягивал картинку по ширине, и
  «вертикальный масштаб 10:1» на экране был вовсе не 10:1. Починка —
  `syncProfileViewBox()`: viewBox выставляется равным реальному размеру
  элемента, единица становится пикселем, и заявленный масштаб честен. Заодно
  отпала поправка на растяжение при перетаскивании вершины.
- Открывать профиль надо **вписанным** (`exag = null`), а не с фиксированным
  10:1: на реальной оси перепад отметок обычно не влезает в окно при таком
  растяжении, и панель открывалась почти пустой.
- **Вертикальный переход на полилинии сделан по модели плагина**, а не выдуман:
  `LVA_RaisePipeVertical` в `LvaBim` режет трубу на 5 частей — стык, стояк,
  поднятая середина, стояк, стык. Все переломы вертикальные и на одной прямой
  в плане, поэтому отводы потом подбирает сам Civil. Во вьювере так же:
  `applyVerticalTransition()` вставляет по две вершины с ОДИНАКОВЫМИ X/Y в
  каждой из двух указанных точек. Уедет план хоть на сантиметр — отводы не
  сядут, а в изометрии это не видно; поэтому проверка в `npm run smoke`
  меряет именно снос стояка в плане, а не «что-то изменилось».
  Раскладка после вставки: `[… A.i, aRise, aTop, …середина…, bTop, bFall, …]`,
  и вторая пара сдвинута ещё на две позиции, т.к. вставка у B идёт первой.
  Индексы стояков: `[A.i+1, A.i+2]` и `[B.i+3, B.i+4]` — считать «с конца»
  нельзя, за участком обычно есть ещё вершины (на этом уже ошибся).
- **Проверки, которые меняют состав вершин, нельзя ставить в середину
  `checkDrawDxf`.** Соседние проверки (число вершин в DXF, длина после
  сопряжения, счёт ручек) считают их по снимку, снятому раньше, — вставка
  четырёх вершин роняет сразу три из них. И брать чужую линию тоже нельзя:
  к концу функции список переживает две очистки, снятый раньше `id` указывает
  в пустоту. Такая проверка чертит СВОЮ линию числами
  (`drawPointByNumbers` + `finishDrawnPolyline`) — предсказуемо и ни с чем
  не пересекается.
- Подписи полилинии (длина, уклон, отметка вершины) живут в **своём** слое
  `#polyline-annot`, а не в `#labels-container`: тот целиком чистится
  `clearMeasureAll()` — ровно так уже теряли метки координат. Источник точек
  общий для черновика и раскрытой линии (`polylineAnnotSource()`), а пересборка
  DOM происходит по смене ключа `тег:число точек:замкнутость` прямо в кадре —
  иначе пришлось бы звать её из каждого места, где добавляется точка.
- **Зум колесом в орто-проекции двигал камеру вбок вместо приближения.**
  `zoomCameraTowardPoint()` — это дольли: камера физически едет к точке под
  курсором, и для перспективы это и есть зум. У ортокамеры масштаб задаёт
  только фрустум (`orthoCamera.top/bottom/left/right` в `syncOrthoFrustum()`),
  расстояние до цели на параллельную проекцию не влияет вообще. Дольли-код
  всё равно исполнялся и двигал `camera.position`/`controls.target` к точке —
  визуально это чистый снос по XY без единого пикселя зума. Починка: в
  `zoomCameraTowardPoint()` при `projectionMode === 'ortho'` дополнительно
  зовём `syncOrthoFrustum(текущая_высота × factor)` — тем же `factor`, что и
  для дольли, поэтому направление (колесо вверх = приближение) не разъезжается
  между проекциями. Закреплено в `npm run smoke` (`checkViewCube`):
  `BimLvaDebug.orthoFrustumHeight` до/после `page.mouse.wheel()`.
  На линейных объектах (километры) старый порог «мягче, если dist > 40 м»
  оставлял колесо мёртвым: луч мимо трубы → `ZOOM_FACTOR_EMPTY * 40/dist`.
  Порог теперь от `lastSceneMaxDim`, на большой сцене шаг ещё растёт.
  Сетка после загрузки файлов выключается (`setSceneGridForLoadedModels`):
  120 м у нуля на трассе — крошечный квадрат в центре, не «земля».
- **Откосы до рельефа реализованы** (кнопка «△ Откосы» в списке полилиний,
  `computeSlopeCrossSection`/`computeSlopeSide`/`buildSlopeToTerrain`):
  влево/вправо/в обе стороны, отдельные 1:m для насыпи/выемки, линия выхода —
  обычная редактируемая полилиния, объём — методом средних площадей по
  сечениям с найденной землёй (как картограмма). Отладочный API пополнился
  `createPolylineFromPoints` (полилиния прямо из точек сцены, без кликов —
  вход для тестов, где нужна точная бровка) и `buildSlopeOnPolyline`/`slopes`.
  **Грабля при написании теста**: фикстура `smoke-grid.ifc` (сетка коробок)
  без геодезических координат центрируется вьювером по СВОЕЙ ограничивающей
  рамке (`forceCenterFragmentsNearOrigin`) — отметка верха коробок в сцене не
  «3» (как в самом IFC-файле), а `3 − sizeZ/2` от центрирования. Держать
  отметку земли числом в тесте нельзя, снимать через
  `BimLvaDebug.modelBounds` (`centerZ + sizeZ/2`) в момент прогона.
  У замкнутого контура середина — ear clipping в плане (`triangulateRingXY`),
  иначе TIN это только борта и в середине дыра; у разомкнутой торцы закрываются
  откосом вдоль оси. Выгрузка: DXF слой `LVA_SLOPE` (3DSOLID) и LandXML 1.2
  Surface (`Pnts`/`Faces`, northing=Y easting=X — как читает сам вьювер и
  Civil 3D Import LandXML). API: `slopeTin`, `slopeLandXml`.
  **КДО и заложение 1:m.** Бока слоёв нельзя вести хордой бровка→выход:
  `exit.z` — выборка земли, а не `brow.z − distance / m`, плюс выход на
  соседнюю площадку вообще не на плоскости откоса. Формула та же, что у
  сечения: `d = mFill · depth` вдоль `section.n`. Кольца лофта не сжимать:
  на глубине 0 веер угла — одна точка, ниже — дуга; `Math.min(len)` после
  дедупа парит грани, и заложение на экране уже не 1:m, хотя `kdoRing` по
  южному ребру ещё зелёный. Крышки триангулировать из сжатого контура.

- **Поперечники по оси — не полилинии.** Линии сечений живут в `roadXsGroup`,
  не в `drawnPolylines`: их десятки, это следствие оси. Правая нормаль в плане:
  касательная `(tx, ty)` → `(ty, −tx)`, смещение > 0 вправо по ходу. На
  переломе секущая — биссектриса правых нормалей входящего и исходящего
  (`miterRightFrame`), scale `1/cos(δ/2)` (cap 8), иначе кромки наезжают
  двумя перпендикулярами — Civil так и оставляет. Шаговые пикеты ближе
  `0.85·width·tan(δ/2)` к PI выкидываются. Промах земли — разрыв
  (`−Infinity`), не ноль, как на профиле. Пикеты: шаг плюс **вершины** оси
  (`pts`), не точки тесселяции дуги в `renderPts` — иначе потолок 200 станций
  съест конец трассы. Чертёж сечения не схлопывать по рельефу: min spanZ = 3 м,
  иначе на плоской площадке линия сливается с осью и окно выглядит пустым.
  Кромки ширины — сплошные (умолч. белые) на самой оси
  (`role === 'road-axis'`), в черновике пока тянешь; сама ось — пунктир.
  Цвет / толщина px / слой DXF оси и кромок правятся в списке полилиний
  и в окне поперечников (`LVA_AXIS` / `LVA_ROAD`). «Удалить все» полилинии
  обязано чистить и поперечники (`clearRoadXsModels`).
  «Построить» лофтит связи шаблона между станциями (`buildRoadCorridor`) —
  иначе на плоской площадке видны только засечки земли и кажется, что кнопка
  ничего не делает. Шаблон не пересобирать связями «по смещению», если есть
  формы: у покрытия две точки на одном off (верх и низ). Пересборка линий
  сечения (`buildRoadXsLines`) не должна снимать полотно. Профиль оси —
  тот же `openPolylineProfile`, не второй движок.

- **Удаление полилинии не по старому индексу.** `deleteDrawnPolyline` сначала
  зовёт `removeSlopeModelsForPolyline`, а та через `dropPoly` уже вынимает
  линию выхода из `drawnPolylines`. Индекс, снятый до этого, указывает на
  соседа: его вычёркивают из списка, объект в `drawGroup` остаётся — в
  таблице «полилиний нет», а контур на площадке виден. После dropPoly искать
  запись заново по id; в конце сверять детей `drawGroup` с записями
  (`purgeOrphanDrawObjects`). Повторное «Построить» по той же бровке
  заменяет старое построение, а не копит вторую площадку.

## 10. Производительность вьювера — что измерено и что осталось

**НАЙДЕНО И ПОДТВЕРЖДЕНО ЗАМЕРОМ, НО ЕЩЁ НЕ ПОЧИНЕНО: механизм снижения
качества при вращении мёртв ровно на больших моделях.** Код на месте:
`controls.addEventListener('start')` роняет `setPixelRatio(1)`, а
`applyRenderQuality()` включает «тяжёлый» режим. Оба порога считают
`allMeshes.length`. Но батчинг (от `IFC_BATCH_THRESHOLD` = 2000 фрагментов)
склеивает модель в считанные меши: замер на сетке **20 000 элементов дал
`allMeshes.length === 1`**, то есть

- `allMeshes.length > 8000` (снижение при вращении) — НЕ срабатывает;
- `allMeshes.length > 12000` (`applyRenderQuality`) — НЕ срабатывает;
- `allMeshes.length > 15000` (отключение зума к курсору) — НЕ срабатывает.

На 4K-экране крупная модель крутится на полной пиксельной плотности — вчетверо
больше работы, чем задумано. Спасает только авто-`perfMode` от трёх файлов в
сводке (`ifcCount >= 3`); один большой файл под него не попадает.
Починка (по убыванию отдачи, владелец пока не давал добро):
1. считать тяжесть по треугольникам или `totalElements`, а не по объектам сцены —
   это оживит уже написанный код;
2. не гонять DOM каждый кадр: `updatePolylineHandles`,
   `updatePolylineAnnotations`, метки и подписи координат проецируются
   **безусловно на каждом кадре**, даже когда сцена не перерисовывается
   (`sceneNeedsRender` их не прикрывает);
3. сильнее ронять разрешение на время движения с восстановлением через ~150 мс.

⚠️ FPS в песочнице мерить бесполезно: headless-Chromium рисует программно
(SwiftShader), без GPU. Числа «стало X кадров» оттуда брать нельзя.

**Счётчик памяти в статус-баре** (`#memReadout`, справа от FPS): «ОЗУ N МБ ·
модели M МБ». Грабли, на которые уже наступил:
- `performance.memory` — **только Chrome**, и он сознательно огрубляет числа
  (защита от side-channel). Точными их считать нельзя, годятся для «до и
  после». В других браузерах показываем один свой счёт моделей, а не ноль.
- **Видеопамять сюда не входит вовсе** — браузер её не отдаёт. То есть
  «модели M МБ» это буферы в куче JS, а не то, что уехало в GPU.
- Вес моделей считается ОДИН раз при загрузке (`modData.geometryBytes`).
  Обходить фрагменты на каждое обновление счётчика нельзя: на файле АР это
  730 000 итераций дважды в секунду — счётчик стоил бы дороже, чем показывает.
  Батч держит свою склеенную копию вершин рядом с исходными фрагментами,
  отсюда ×2 у батченых моделей.
- Целые мегабайты врали на мелких моделях («0 МБ» при 0.4 МБ) и счётчик
  выглядел сломанным — до 10 МБ печатаем десятую долю.

**Про GPU.** Отрисовка УЖЕ на GPU — three.js через WebGL2, иначе 700 000
элементов не крутились бы вовсе. На CPU и в один поток остальное: разбор STEP
и тесселяция в web-ifc (WASM), построение BVH, батчинг. Поэтому «прикрутить
GPU» к загрузке нечего — там нечего распараллеливать на шейдерах. Реальные
пути ускорения загрузки: (а) кэш геометрии — сделан, §кэш ниже; (б)
**`web-ifc-mt` (многопоточный WASM) уже вендорится** (`web-ifc-mt.wasm`,
`web-ifc-mt.worker.js` в `tools/vendor.mjs`), но вьювер его НЕ использует —
это неиспользованный запас, требует COOP/COEP-заголовков, а их на GitHub Pages
не поставить; (в) WebGPU-рендерер three — это про отрисовку, не про загрузку.
