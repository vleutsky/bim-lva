## 4. Лицензии — контракт (единственный источник правды)

Формат придуман **не нами**: он уже реализован в
`LVA.BIM.Common\Licensing\` (`LicenseGate.cs`, `LicenseModels.cs`) и в
`Tools\New-LvaLicense.ps1`. Веб подстроен под него. **Ничего здесь не менять,
не сверившись с C#.**

- Алгоритм: **RSA-SHA256, PKCS#1 v1.5** (не Ed25519 — была такая ошибка).
- Продукты: ровно `Civil`, `Navis`, `Inventor`, `*`. Других нет.
- Привязка к железу: `HostLock` = SHA-256 от
  `Win32_ComputerSystemProduct.UUID` (Trim → UpperInvariant → UTF8 → hex X2),
  64 hex-знака. Клиент получает его через `Tools\Get-LvaMachineId.ps1`.
- Каноническая строка:
  `LicenseId|ClientName|Products(через запятую)|IssuedUtc|ExpiresUtc|HostLock`
  Бессрочная — пустая строка в позиции `ExpiresUtc`, не `null`.
- **Даты — .NET `ToString("o")`: семь знаков дробной части.** JS `toISOString()`
  даёт три, и подпись не сходится после разбора JSON в C#. Для этого есть
  `toDotNetRoundTrip()`; на это завязана половина `npm run test-license`.
- Файл `license.lic` = JSON `{ Payload, Signature }`.
- **Бессрочная лицензия в UI:** `expires_at = null` нельзя гонять через
  `new Date(null)` — выйдет 1970 год и статус «Истекла». Офлайн-скрипт без
  `-ExpiresUtc` выдаёт именно бессрочные, так что после импорта это видно сразу.
  Оба места в `cabinet.html` (список получателя и таблица админа) прикрыты, за
  этим следит `npm run test-license-import`.

Ключи:

- Ключ подписи **кода** («LVA Code Signing») остаётся офлайн, в облако не уезжает.
- Для веба — **отдельная** пара: `tools/New-LvaWebKey.ps1` (RSA-3072,
  `New-SelfSignedCertificate`; на PS 5.1 нужен openssl из Git for Windows).
  Приватная часть → секрет `LICENSE_SIGNING_KEY` в Supabase, `pubkey-web.cer` →
  в `LVA.BIM.Common\Licensing\` и пересборка. `LicenseGate.VerifySignature`
  перебирает **все** встроенные `.cer`, поэтому старые лицензии не ломаются.
- Приватный ключ генерируется **только на машине владельца**. В чат, в репозиторий
  и в коммиты он не попадает никогда. `license-keys/` в `.gitignore`.
- Статический сайт — **не защищённое место**. Генератор ключей в браузере
  опубликовал бы секрет. Выпуск живёт только в Edge Function под `service_role`.
- `adminEmails` в `auth-config.js` — удобство UI, **не** защита. Права решает
  таблица `license_admins`.

## 9. Грабли (уже наступали)

- **Не выдумывать состав продукта.** Список плагинов, кнопок и продуктов брать
  из кода `LvaBim`. Дважды придумывался несуществующий перечень — оба раза мимо.
- **Не проектировать поверх непрочитанного.** Схема лицензий была построена с
  нуля (Ed25519, привязка к email+организации), хотя в репозитории уже работала
  своя — RSA и node-lock. Переделывать пришлось целиком.
- `tools/New-LvaWebKey.ps1` без UTF-8 BOM ломался на Windows PowerShell 5.1:
  без BOM файл читается в системной кодировке (у владельца — cp1251), кириллица
  в комментариях и строках превращается в крякозябры, и часть из них случайно
  складывается в символы вроде `"`/`}` — парсер валится на «непредвиденный
  токен» в местах, весьма далёких от настоящей причины. PS 7 эту же кодировку
  угадывает верно и без BOM — поэтому в песочнице (нет PS 5.1) баг не ловился.
  Чинится добавлением BOM (`\xef\xbb\xbf` первыми байтами файла) — дальше и
  PS 5.1, и PS 7 читают его как UTF-8 одинаково. Если появятся другие `.ps1` в
  этом репозитории — сразу с BOM, не постфактум.
- Тот же скрипт: уборка временных файлов в `finally` (`Remove-Item $pfx/$pem/...`)
  роняла **весь** запуск на Windows PowerShell 5.1 из-за глобального
  `$ErrorActionPreference = 'Stop'` — если `Remove-Item` не мог удалить файл
  (на профиле владельца путь пользователя с точкой в имени даёт короткое
  8.3-имя, `Test-Path` и `Remove-Item` иногда расходятся на таких путях), это
  превращалось в завершающую ошибку и обрывало скрипт **после** того, как
  приватный ключ уже был посчитан, но **до** записи `private-key.b64` на диск —
  то есть вся работа терялась на последнем шаге. Починка: `Remove-Item ...

  `RefDirection = $` у `WorldCoordinateSystem` — поворота там правда нет — и

  скопировал: `RefDirection`=(cos α, sin α) даёт локальную ось X, поэтому
  угол — `atan2(y, x)`. `TrueNorth`=(Tx, Ty) — это направление истинного
  севера ОТНОСИТЕЛЬНО оси Y модели, поэтому угол, выравнивающий его с мировой
  осью Y — `atan2(Tx, Ty)` (компоненты в обратном порядке). Вывод через
  матрицу поворота: `R(θ)·(Tx,Ty) = (0,1)` разрешается в `θ = atan2(Tx,Ty)` —
  расписано в комментарии у `readWorldCoordinateSystemShift`. Числа сошлись
  сами по себе (не подгонял): `atan2(-0.20894, 0.97793) = -12.060°` — то же

  стоял в разных точках — на уклоне пара метров набегает честно. Сравнивать
  надо min/max.
- **НАЙДЕНО И ПОЧИНЕНО: сводка на ЗАВОДСКОЙ сетке (~1200 м) разъезжалась.**
  Файлы из Tekla (АС и КМ, координаты общие и согласованные, в Navisworks
  садятся нормально) во вьювере разлетались на километр. Две причины,
  складывались:
  1. `LARGE_COORD_THRESHOLD` = 5000 м. Заводская сетка под него не проходит →
     файл не привязывается к общему нулю → `forceCenterFragmentsNearOrigin`
     сажает КАЖДЫЙ файл в свой центр, и взаимное положение уничтожается.
     Точность тут ни при чём: на 1200 м шаг float32 ≈ 0.14 мм. Починка —
     отдельная константа `SELF_CENTER_MAX_COORD` = 200 м: ниже неё модель
     считаем «выгруженной в своём нуле» (её и центрируем, как раньше), выше —
     координаты осмысленные и трогать их нельзя.
  2. `snapSceneContentToOrigin()` записывает свой сдвиг ТОЛЬКО в
     `ifcWorldOrigin`. Нуля нет — записать некуда: уже загруженные модели
     уезжают в ноль, а следующий файл приходит со своими настоящими
     координатами и оказывается за километр (замерено: 1608 м вместо 116.7).
     Починка — без нуля не двигаем ничего.
  ⚠️ Правка №1 сначала была сделана по порогу 5000 м и **уронила smoke**:
  фикстура `smoke-grid.ifc` (центр ≈ 80 м) перестала центрироваться, а тесты
  откосов чертят полилинии по фиксированным X/Y и промахнулись мимо модели
  («no-ground»). Отсюда и взялась отдельная константа 200 м.
  Закреплено в `npm run test-plant-grid` (числа из реальных файлов: IfcSite
  1242.0/1148.5 и 1194.6/1055.5). Проверять надо РАЗНОС между моделями:
  абсолютных координат мало, сцена законно до-центрируется и уводит обе.
- **НАЙДЕНА И ПОЧИНЕНА настоящая причина «файлы Tekla разъезжаются».**
  Приём разбора, который сработал: владелец намерил во вьювере 1708.94 м
  между двумя файлами, а в Navisworks — 116.15 м. Центр АС по Navisworks
  1231.43/1171.43/61.80, его модуль ≈ 1700.7 м — совпало с намеренным. Раз
  расстояние между моделями равно расстоянию от нуля до одной из них, значит
  вторая сидит В НУЛЕ, а не «немного уехала». Числа для сверки берутся из
  Navisworks: «Преобразовать центр» в свойствах файла даёт центр модели в
  мировых координатах. Добил показ габарита ДО вычитания нуля сцены («Анализ →
  CRS»): у КМ он оказался коробкой 18×12×7 м вокруг нуля — то есть координаты
  потеряны ЕЩЁ ДО координатного конвейера вьювера, их обнулил сам web-ifc.
  Две причины, обе починены:
  1. **`countIfcBooleanOps` не считал `IFCBOOLEANCLIPPINGRESULT`** —
     регулярка была `/IFCBOOLEANRESULT\s*\(/`, а `IFCBOOLEANCLIPPINGRESULT`
     это ОТДЕЛЬНЫЙ тип и под неё не подходит. У Tekla именно он и составляет
     почти все вырезы (в файле АС: 1613 clipping из 1997 булевых). Счёт
     занижался в разы, а от него зависят и `USE_FAST_BOOLS`, и решение о
     сбросе координат. Из-за этой же дыры первая версия теста НЕ воспроизвела
     поломку (`cto=false`) и чуть не увела в сторону.
  2. **Порог правила Tekla в `shouldForceCoordinateToOrigin` был 50 м:**
     `isTekla && isIfc2x3 && booleans >= 8 && worldMeters >= 50`. Под него
     попадает ЛЮБАЯ выгрузка промплощадки (координаты ~1200 м), и файл
     открывался с `COORDINATE_TO_ORIGIN` — координаты терялись безвозвратно.
     Поднят до `LARGE_COORD_THRESHOLD`: на 1200 м шаг float32 = 0.14 мм,
     жертвовать координатами ради точности CSG не за чем. Если геометрия
     всё-таки выйдет пустой, загрузка сама переоткроет файл с CTO (повтор уже
     есть в коде) — по факту, а не по догадке.
  Закреплено в `npm run test-plant-grid`: фикстуры воспроизводят выгрузку
  Tekla (IFC2X3, мм, 1997 и 294 выреза, центры из Navisworks). До правки
  тест давал ошибку 1699 м и `ПОСАЖЕН В СВОЙ ЦЕНТР` — ровно симптом владельца.
  `BimLvaDebug.modelAbsExtents[].cto` показывает, открыт ли файл со сбросом.
  Предупреждение о сбросе теперь срабатывает от `SELF_CENTER_MAX_COORD`
  (200 м), а не от 5000 м — на заводской сетке вьювер об этом МОЛЧАЛ.
  **Уточнение (КМ ~1195 м, 397 вырезов):** упреждающий CTO на 1200 м уже
  выключен, но файл всё равно мог открыться «со сбросом»: (1) кэш геометрии
  сохранял старые `openSettings.COORDINATE_TO_ORIGIN=true` и подсовывал
  меши у нуля; (2) повтор при пустой тесселяции всё ещё включал CTO и
  оставлял модель у нуля — GetCoordinationMatrix нули, вернуть сдвиг
  web-ifc не умеет. Починка: кэш со сбросом, если политика уже другая,
  отбрасываем; после CTO сажаем фрагменты по крупным `IFCCARTESIANPOINT`
  файла (Z-up → Y-up web-ifc). Предупреждение «Поставьте Выравниванием»
  только если восстановить не вышло.
- **Восстановление после CTO: якорь по МАТРИЦАМ вставки, выборка точек — запасной.**
  Сброс координат у файлов Tekla приходит не от правила (порог поднят), а от
  повтора «геометрия вышла пустой → переоткрыть с COORDINATE_TO_ORIGIN»: без
  CTO web-ifc такую CSG не строит вовсе. Восстанавливать положение по центру
  крупных `IFCCARTESIANPOINT` из текста можно, но это ПРИБЛИЖЕНИЕ — замерено
  **3.67 м мимо** на фикстуре (точки из текста это точки вставки, а не центр
  геометрии). Точный якорь — центроид матриц вставки, снятый ДО переоткрытия:
  web-ifc отдаёт их в double, и они верны даже когда тесселяция вырождена
  (вершин нет, матрицы есть). После повтора берётся тот же центроид, разница и
  есть сдвиг. Выборка точек осталась запасным путём — на случай, когда CTO
  решён заранее и пред-прохода не было.
  ⚠️ Сдвиг снимается ДО `scaleIfcFragmentsToMeters`, поэтому при применении его
  надо домножать на `modData.lengthToMeters` — иначе на мм-файле промах в 1000 раз.
  ⚠️ Проверить это на синтетике нельзя: у фикстуры геометрия не вырождается.
  Поэтому есть крючок `BimLvaDebug.forceCtoRetryOnce()`. Его надо переставлять
  ПОСЛЕ каждой ветки, пересчитывающей `usableCount` (ветка кэша геометрии его
  съедала, и тест показывал `cto=false`).
  Закреплено сквозной проверкой в `npm run test-plant-grid`: ошибка 0.00 м
  против 3.67 м у восстановления по тексту.
- **`COORDINATE_TO_ORIGIN` ломает сводку.** web-ifc сдвигает им *каждый* файл к
  его собственному центру и не сообщает, на сколько (`GetCoordinationMatrix`
  возвращает нули — проверено). Включённый «для всех геодезических моделей», он
  схлопывал шесть файлов одной дороги в кучу у нуля; габариты при этом
  правильные, поэтому по ним поломка не видна. Включать только против float32-
  тесселяции CSG (много boolean). Без CSG вершины локальны, а мировое
  положение живёт в `flatTransformation` (double) — точность цела.
  Закреплено проверкой `checkGeoFederation` в `npm run smoke`.
- Схемы IFC4X1/IFC4X2 (Civil 3D, OpenRoads) web-ifc парсит нормально, хотя
  официально не заявляет: DATA-секция читается без оглядки на `FILE_SCHEMA`.
  Открываем их с предупреждением, а не отказом.
- **Карта-подложка: Яндекс/Google/2ГИС нельзя** — не технически, а по лицензии:
  их условия разрешают показывать карту только внутри их виджета, а нам нужна
  картинка текстурой под 3D. Bing Microsoft сворачивает в пользу Azure Maps.
  Остаются OSM (с оглядкой на их tile usage policy), спутник ESRI и свой
  шаблон MapTiler/Mapbox с ключом **пользователя** (в HTML ключ класть нельзя).
- **«Рельеф с карты» — меш, не картинка.** Подложка и OpenTopoMap с горизонталями
  землю не отдают: `sampleTerrainZ` пропускает `isGeoRaster`. Кнопка в диалоге
  карты качает сетку высот (AWS Terrarium без ключа; Terrain-RGB — свой ключ,
  как у подложки) и собирает обычный меш (`isMapTerrain`, не `isGeoRaster`).
  Тот же охват и привязка, шаг ~10–30 м. Для объёмов и посадки здания по-прежнему
  LandXML/IFC/свой растр. Георастр из выборки рельефа выкинут специально, чтобы
  текстура не считалась поверхностью.
- **Глобус «Площадка с карты»: повторное открытие держит `mapBld` в памяти.**
  Колесо до зума 2 показывает весь мир, а `openMapBuilderModal` раньше не
  возвращал HOME. Поиск Nominatim с github.io часто 403 (User-Agent браузер
  не ставит); подпись в углу могла остаться от прошлого успеха, вид — нет.
  Фикс: min zoom 6, при `zoom < 10` восстанавливаем lastGood / привязку / СПб;
  «Санкт-Петербург» и «Москва» — локальные алиасы до fetch. Закреплено в
  `npm run test-basemap` (A-h reopen, A-i поиск СПб против мока Челны).
- **Площадка с карты: два режима координат.** На пустой сцене «в нули» сажает
  центр рамки в (0, 0) плана (отметка Z — Terrarium, не ноль). «Мировые» —
  поперечная Меркатора 6° на WGS84 (как Гаусс–Крюгер, не SK-42): зона
  `floor(lon/6)+1`, восток `zone·1e6+500000`, меш в мировых E/N, сцена у нуля
  за счёт `ifcWorldOrigin` (`worldOriginFrame = 'external'`), иначе float32 на
  миллионах метров. Это не МСК площадки. Если модель уже есть — переключатель
  игнорируется, якорь = центр модели. `ensureSceneContentNearOrigin` без модели
  не зовём: snap видит сырые вершины карты и повторно вычитает их из origin.
  Закреплено в `npm run test-basemap` (A-k нули, A-l мировые).
- **После «Загрузить» с глобуса включать всю ленту сцены**, не только
  «Полилиния» и «Замер». `syncEmptySceneChrome` оставлял ось, площадки и
  тело выключенными — на площадке с карты нельзя было строить.
- Тайл-серверы из песочницы **закрыты прокси** (OSM, ESRI, Яндекс, S3 — все FAIL,
  npm при этом отвечает). Поэтому `npm run test-basemap` мокает тайлы через
  `page.route` и проверяет математику, а не сеть. Terrarium — сплошной PNG
  известной высоты (формула `(R·256+G+B/256)−32768`), не 1×1 прозрачный.
  Текст в диалоге карты, который должен остаться на экране, нуждается в `id`:
  безымянные `.bulk-note` палитра при инициализации снимает в кнопку «?»
  (`dataset.tip`, обрезка 700 знаков) — предупреждение про DEM без `id`
  из диалога пропадало.
- **Меркатор ≠ метры.** Проекция растягивает всё в 1/cos(широты) раз (для 55.7°
  это 1.77×). Наивное «метр в метр» даёт правдоподобную, но целиком смещённую
  подложку. Поэтому UV подложки считается через `uvFor`: точка модели →
  широта/долгота → пиксель Меркатора. Линейный UV дал бы в центре ровно
  (0.5, 0.5) — на этом и построена проверка в тесте.
- Границы георастра — в **абсолютных** координатах (easting/northing), сдвиг
  нуля сцены компенсирует позиция `geoRasterGroup`. Поэтому драпировка и высота
  требуют поправки `worldShift`, иначе луч уходит за тысячи километров, а
  плоскость всплывает на высоту origin.
- Оси: web-ifc отдаёт геометрию в **Y-up** (E, h, −N), `globalGroup.rotation.x
  = π/2` разворачивает её в сцену **Z-up** (E, N, h). `ifcWorldOrigin` хранится
  в Y-up-системе — отсюда `currentWorldShiftEN()`.
- **Текстовый индекс IFC ленивый, и `ifcIndex` больше НЕ признак «это IFC».**
  Раньше наличие `ifcIndex` играло две роли сразу: сам индекс и флаг
  «модель редактируется» (35 проверок из 48). Сделать его ленивым, не разведя
  роли, нельзя — экспорт, фильтр классов, ведомость и объединение молча
  решили бы, что IFC не редактируется. Теперь: `canEditIfc(mod)` —
  синхронный признак (есть индекс ИЛИ есть файл), `hasIfcIndex(mod)` —
  «уже построен», `ensureIfcIndex(mod)` — асинхронное построение по запросу.
  Любая новая операция, читающая STEP-текст, обязана сначала
  `await ensureIfcIndex(...)` (или `ensureIfcIndexes` для всех моделей).
- **Кэш геометрии: в кэш идёт СЫРОЙ вывод `StreamAllMeshes`, а не готовая
  сцена.** Соблазн сложить вершины в абсолютные координаты и не хранить
  матрицы вставки силён (кэш стал бы меньше и проще), но на геодезической
  модели (55 300 м) float32 даёт шаг ≈4 мм — кэш сам бы двигал модель, ровно
  та же ловушка, из-за которой `COORDINATE_TO_ORIGIN` включается только против
  float32-CSG. Поэтому в записи локальные вершины (float32, как их отдал
  web-ifc) и матрица отдельно (float64), а весь конвейер после потока
  (единицы → WorldCoordinateSystem → ноль сцены) на кэшированном пути
  выполняется заново: он зависит от того, какие модели уже открыты, и «запечь»
  его значило бы посадить файл относительно случайного соседа по прошлой
  сводке. Закреплено в `npm run test-geom-cache` на геодезической фикстуре —
  на фикстуре у нуля потеря точности не видна вовсе.
- **Что кэш даёт по времени — мерить фазу геометрии, а не всё открытие.**
  Замер на сетке 20 000 коробок: сама фаза геометрии 464 → 104 мс (4.5×), а
  всё открытие 2743 → 2034 мс (1.35×). Разница потому, что старт страницы,
  инициализация WASM, `OpenModel`, батчинг, BVH и дерево остаются как были.
  Смотреть «стало ли быстрее» по общему времени — верный способ решить, что
  кэш бесполезен. Для этого в консоль печатается строка
  `геометрия из кэша|тесселирована за N мс`, а в тестах есть
  `BimLvaDebug.geomCache.phaseMs(файл)`.
- **Тест кэша нельзя синхронизировать по `modelBounds`.** Габариты появляются
  РАНЬШЕ, чем загрузка доходит до записи кэша, и проверка «первое открытие
  заполнило кэш» падала на пустой базе, хотя запись потом проходила. Конец
  загрузки — включение `#clear` в хвосте `loadFilesSequentially` (та же
  грабля, что с кнопками при массовой загрузке).
- **Замер памяти в V8: временные массивы утекают в результат.** Первый вариант
  бенчмарка индекса выдавал ОТРИЦАТЕЛЬНУЮ стоимость — сборщик убирал массив
  кусков текста уже после базовой отметки. Строить данные надо в функции,
  чтобы временное гарантированно исчезло до замера, и мерить каждую схему
  в своём процессе с `--expose-gc` и двойным `gc()`.
  Числа (730 000 сущностей): старая схема (массив строк + объекты) 83.7 МБ,
  новая (смещения в Int32Array) 28.0 МБ. На реальном файле АР владелец
  намерил старую в 64.2 МБ — плюс ~82 МБ текста, который она удерживала.
- **`split()` в V8 не копирует текст, а делает срезы на исходную строку.**
  Поэтому массив строк удерживает весь файл целиком, и отпустить его нельзя,
  пока жив хоть один элемент. Измерено: после освобождения исходной строки
  не освобождается ничего. Отсюда и переход на смещения.
- **Толщину линии в WebGL обычной `THREE.Line` задать нельзя.** `linewidth` у
  `LineBasicMaterial` молча игнорируется почти везде — это ограничение WebGL,
  не three. Поэтому начерченные полилиний — `Line2` + `LineGeometry` +
  `LineMaterial` (вендорится, см. `THREE_ADDONS` в `tools/vendor.mjs`). Цена:
  у `Line2` НЕТ атрибута `position` — позиции лежат в `instanceStart`/
  `instanceEnd`, поэтому всё, что читало геометрию линии напрямую, надо
  переводить на свой список точек (`record.renderPts`); на этом уже
  спотыкался `sweepAxisPoints()`. Ещё `LineMaterial` держит разрешение
  холста в пикселях — его надо обновлять в `resize()`, иначе толщина
  разъезжается при смене размера окна.
- **Выбор линии кликом сделан своим пикингом, а не `Line2.raycast`.** У Line2
  raycast экранный и зависит от `material.resolution` и от `linewidth`
  (порог = `linewidth + threshold`), то есть область попадания растёт вместе с
  толщиной линии. Вместо него — проекция `renderPts` через `projectToPixels()`
  и порог в **пикселях** (`POLYLINE_PICK_PX`), как у объектной привязки:
  предсказуемо и не зависит от стиля линии.
  ⚠️ При отладке пикинга по линии: точка клика и вершина полилинии **не
  совпадают** — объектная привязка уводит поставленную точку на ближайшую
  вершину геометрии (до ~12 px). Целиться надо в спроецированные вершины
  (`BimLvaDebug.polylineScreenPts`), иначе кажется, что пикинг сломан. На это
  уже потрачено время впустую.
- **Промах луча вниз — это не ноль и не «низ сцены».** В профиле по оси и в
  картограмме за краем поверхности отметки просто НЕТ. Маркером промаха служит
  `-Infinity`, переданный в `sampleTerrainZ` как fallback: сравнивать с обычным
  числом нельзя — оно может совпасть с настоящей отметкой. Такие пикеты дают
  разрыв линии и прочерк в таблице, а их число печатается. Подставить туда
  число значило бы соврать в чертеже.
- Площадь в картограмме считается по ячейкам с **найденной** землёй
  (`measured`), а не по всем внутри контура: только она соответствует
  посчитанному объёму. Иначе «объём / площадь» врал бы там, где часть контура
  висит над пустотой. На этом же построен точный тест: подъём проектной
  отметки на Δ обязан изменить баланс ровно на `площадь × Δ`.
- Азимут в вводе точки числами — геодезический: **по часовой от севера**,
  поэтому `dx = L·sin(A)`, `dy = L·cos(A)`, а не наоборот. Оси сцены Z-up:
  X — восток, Y — север. В тесте это ловится шагами на 90° и 0°.
- Таблица вершин полилинии перебирает `pts` (реальные вершины), а **не** `abs`:
  после сопряжения в `abs` лежат ещё и точки дуг, и нумерация строк разъедется
  с `radii`. На этом уже попадался — строки таблицы указывали не на те вершины.
- **Догрузка файла пересобирает меши — и стирала назначенный цвет.** Добавление
  файла зовёт до-центрирование сцены, оно двигает вершины и вызывает
  `rebuildIfcMeshesFromFragments()`. Батчи (`buildIfcBatches`) цвет из
  `appearanceByID` читали, а `addIndividualIfcMeshes()` — нет, и строила
  материалы из исходных цветов фрагментов. То есть у моделей МЕНЬШЕ порога
  батчинга (2000 фрагментов) покраска слетала при каждом добавлении файла.
  Теперь `addIndividualIfcMeshes` в конце возвращает сохранённое оформление.
- **Камеру вписываем только на ПЕРВОЙ загрузке.** `fitView()` стоял после
  каждой пачки, и добавление файла уводило пользователя с того места, куда он
  сам отзумился. Флаг `sceneWasEmpty` снимается в начале
  `loadFilesSequentially`. Проверять это через `cameraTarget` бесполезно:
  сцена до-центрируется, и цель остаётся у нуля в обоих случаях — сверять надо
  `cameraPos`.
- **Подсветка выделения оставалась навсегда на покрашенных элементах.** Снятие
  выделения идёт через `setEmissive(mesh, 0)` → `reapplyAppearanceForItem()`.
  Там две ветки: без оформления — `restoreMeshOriginalAppearance()`, она
  emissive гасила; с оформлением — `applyAppearanceToMesh()`, а она его не
  трогала вовсе. Теперь гасит и она, а `applyAppearanceToSelection()` возвращает
  подсветку тем, кто ещё выделен. После «Применить оформление» выделение
  снимается: под подсветкой назначенный цвет всё равно не разглядеть.
- **Не перестраивать таблицу, пока в ней набирают.** Профиль перерисовывается
  из десятка мест, и каждая перерисовка подменяла поле ввода новым — введённое
  пропадало на месте, а клик по полю вообще сбрасывал значение (обработчик
  подсветки строки перерисовывал таблицу прямо на клике). `renderProfileTable`
  теперь пропускает пересборку, если фокус внутри таблицы, а клик по
  `input/select/textarea` не считается выбором строки.
- **Профиль по оси показывает ВЕРШИНЫ, а не пикеты с шагом.** Шаг пикета
  убран из панели: промежуточные точки на прямой между вершинами ничего не
  сообщают, а таблицу раздувают до сотен строк. Земля при этом по-прежнему
  опрашивается часто (шаг = длина/400, подбирается сам) — иначе синяя линия
  срезала бы складки рельефа. То есть два разных ряда: густой для отрисовки
  земли и по вершинам для таблицы и правки.
- Пикет вершины меряется вдоль **renderPts** (с дугами), а сами вершины берутся
  из **pts** — иначе номера строк разъедутся с вершинами, как уже было в
  таблице полилинии. Вставка по пикету поэтому идёт в два шага: точка на
  renderPts → `nearestPolylineSegment()` → вставка между pts.
- `preserveAspectRatio="none"` у SVG профиля растягивал картинку по ширине, и
  «вертикальный масштаб 10:1» на экране был вовсе не 10:1. Починка —
  `syncProfileViewBox()`: viewBox выставляется равным реальному размеру
  элемента, единица становится пикселем, и заявленный масштаб честен. Заодно
  отпала поправка на растяжение при перетаскивании вершины.
  **Не поднимать пол viewBox выше реального чертежа** (`Math.max(180, height)`
  при height ≈ 90): HTML-оверлей `#polyProfileAnnot` в CSS-пикселях, а
  `f.py` в единицах viewBox — красные отметки вершин уезжают за край
  (`placeChartLabel` их отбрасывает), зелёный уклон в середине кадра остаётся.
  Снаружи: «на вершине правится только уклон». Таблицу профиля не жать
  `max-height: 72px` — в палитре место есть, высота `--rs-prof-table` и
  ручка `#rsSplitProfileTable`.
- **Вертикальный масштаб профиля по умолчанию — 1:1** (просьба владельца,
  2026-08-20): «авто» вписывало перепад в окно и растягивало отметки на
  произвольную величину, работать с чертежом было нельзя. Горизонтальный при
  этом не трогается ничем — `profileFrame` считает `mPerPxX` только из окна
  пикетажа, вертикаль выводится из него.
  ⚠️ Голое `exag = 1` РОНЯЕТ smoke тремя проверками: на короткой оси с большим
  перепадом натуральный масштаб не помещается в кадр, и подписи отметок,
  уклонов и Rв уезжают за край — `placeChartLabel` их молча отбрасывает, и
  панель выглядит пустой. Именно поэтому раньше стояло «вписать». Поэтому
  умолчание отступает до вписывания, когда иначе не влезает (`exagAuto`), а
  ЯВНО выбранный масштаб держится как есть.
- **Вертикальный переход на полилинии сделан по модели плагина**, а не выдуман:
  `LVA_RaisePipeVertical` в `LvaBim` режет трубу на 5 частей — стык, стояк,
  поднятая середина, стояк, стык. Все переломы вертикальные и на одной прямой
  в плане, поэтому отводы потом подбирает сам Civil. Во вьювере так же:
  `applyVerticalTransition()` вставляет по две вершины с ОДИНАКОВЫМИ X/Y в
  каждой из двух указанных точек. Уедет план хоть на сантиметр — отводы не
  сядут, а в изометрии это не видно; поэтому проверка в `npm run smoke`
  меряет именно снос стояка в плане, а не «что-то изменилось».
  Раскладка после вставки: `[… A.i, aRise, aTop, …середина…, bTop, bFall, …]`,
  и вторая пара сдвинута ещё на две позиции, т.к. вставка у B идёт первой.
  Индексы стояков: `[A.i+1, A.i+2]` и `[B.i+3, B.i+4]` — считать «с конца»
  нельзя, за участком обычно есть ещё вершины (на этом уже ошибся).
- **Проверки, которые меняют состав вершин, нельзя ставить в середину
  `checkDrawDxf`.** Соседние проверки (число вершин в DXF, длина после
  сопряжения, счёт ручек) считают их по снимку, снятому раньше, — вставка
  четырёх вершин роняет сразу три из них. И брать чужую линию тоже нельзя:
  к концу функции список переживает две очистки, снятый раньше `id` указывает
  в пустоту. Такая проверка чертит СВОЮ линию числами
  (`drawPointByNumbers` + `finishDrawnPolyline`) — предсказуемо и ни с чем
  не пересекается.
- Подписи полилинии (длина, уклон, отметка вершины) живут в **своём** слое
  `#polyline-annot`, а не в `#labels-container`: тот целиком чистится
  `clearMeasureAll()` — ровно так уже теряли метки координат. Источник точек
  общий для черновика и раскрытой линии (`polylineAnnotSource()`), а пересборка
  DOM происходит по смене ключа `тег:число точек:замкнутость` прямо в кадре —
  иначе пришлось бы звать её из каждого места, где добавляется точка.
- **Зум колесом в орто-проекции двигал камеру вбок вместо приближения.**
  `zoomCameraTowardPoint()` — это дольли: камера физически едет к точке под
  курсором, и для перспективы это и есть зум. У ортокамеры масштаб задаёт
  только фрустум (`orthoCamera.top/bottom/left/right` в `syncOrthoFrustum()`),
  расстояние до цели на параллельную проекцию не влияет вообще. Дольли-код
  всё равно исполнялся и двигал `camera.position`/`controls.target` к точке —
  визуально это чистый снос по XY без единого пикселя зума. Починка: в
  `zoomCameraTowardPoint()` при `projectionMode === 'ortho'` дополнительно
  зовём `syncOrthoFrustum(текущая_высота × factor)` — тем же `factor`, что и
  для дольли, поэтому направление (колесо вверх = приближение) не разъезжается
  между проекциями. Закреплено в `npm run smoke` (`checkViewCube`):
  `BimLvaDebug.orthoFrustumHeight` до/после `page.mouse.wheel()`.
- **Откосы до рельефа реализованы** (кнопка «△ Откосы» в списке полилиний,
  `computeSlopeCrossSection`/`computeSlopeSide`/`buildSlopeToTerrain`):
  влево/вправо/в обе стороны, отдельные 1:m для насыпи/выемки, линия выхода —
  обычная редактируемая полилиния, объём — методом средних площадей по
  сечениям с найденной землёй (как картограмма). Отладочный API пополнился
  `createPolylineFromPoints` (полилиния прямо из точек сцены, без кликов —
  вход для тестов, где нужна точная бровка) и `buildSlopeOnPolyline`/`slopes`.
  **Грабля при написании теста**: фикстура `smoke-grid.ifc` (сетка коробок)
  без геодезических координат центрируется вьювером по СВОЕЙ ограничивающей
  рамке (`forceCenterFragmentsNearOrigin`) — отметка верха коробок в сцене не
  «3» (как в самом IFC-файле), а `3 − sizeZ/2` от центрирования. Держать
  отметку земли числом в тесте нельзя, снимать через
  `BimLvaDebug.modelBounds` (`centerZ + sizeZ/2`) в момент прогона.
  У замкнутого контура середина — ear clipping в плане (`triangulateRingXY`),
  иначе TIN это только борта и в середине дыра; у разомкнутой торцы закрываются
  откосом вдоль оси. Выгрузка: DXF слой `Откос` (3DSOLID) и LandXML 1.2
  Surface (`Pnts`/`Faces`, northing=Y easting=X — как читает сам вьювер и
  Civil 3D Import LandXML). API: `slopeTin`, `slopeLandXml`.
  **КДО и заложение 1:m.** Бока слоёв нельзя вести хордой бровка→выход:
  `exit.z` — выборка земли, а не `brow.z − distance / m`, плюс выход на
  соседнюю площадку вообще не на плоскости откоса. Формула та же, что у
  сечения: `d = mFill · depth` вдоль `section.n`. Кольца лофта не сжимать:
  на глубине 0 веер угла — одна точка, ниже — дуга; `Math.min(len)` после
  дедупа парит грани, и заложение на экране уже не 1:m, хотя `kdoRing` по
  южному ребру ещё зелёный. Крышки триангулировать из сжатого контура.

- **Пересечения осей: две грабли подряд, обе стоили нескольких заходов.**
  1. **Значение `<select>` — всегда строка, `record.id` полилинии — число**
     (`++drawPolylineSeq`). Диалог заполнялся `option.value = poly.id`, а
     потом `drawnPolylines.find(p => p.id === value)` не совпадало НИКОГДА:
     окно открывалось, оси в списке были, а «Создать» отвечало «не найдены
     полилинии». Симптом уводит в сторону — кажется, что сломан список, а
     сломано сравнение. Починка: `<option>` несёт НОМЕР оси в списке,
     а сам список запоминается в `intersectionDialogState.candidates`;
     поиска по id больше нет вовсе. Так же стоит делать в любом новом
     диалоге, выбирающем объект сцены.
  2. **Геометрию считать в координатах СЦЕНЫ (`record.pts`), не в
     абсолютных.** `intersectionGroup` висит прямо в `scene`, поэтому
     закругления, посчитанные через `worldPointToAbsoluteXYZ`, уезжали на
     весь `ifcWorldOrigin` — у владельца 64 860 м, снаружи это опять
     выглядит как «кнопка ничего не делает». Абсолютные нужны ТОЛЬКО для
     подписи в уведомлении. ⚠️ Тест без загруженной модели этого не ловит:
     без нуля сцены `worldPointToAbsoluteXYZ` возвращает точку как есть, и
     обе версии совпадают. В `npm run test-intersections` поэтому сначала
     грузится геодезическая фикстура — проверено обратной подстановкой
     ошибки: тест даёт 6 провалов и «дальняя точка 64 856 м».
  Закругление — дуга, КАСАТЕЛЬНАЯ к обеим осям (отступ по лучу
  `t = R/tg(φ/2)`, центр на биссектрисе на `d = R/sin(φ/2)`), а не веер
  точек вокруг пересечения, как было в первой версии. Число закруглений
  задаёт тип: крест 4, примыкание 2. Какие ветви узла существуют, решает
  `intersectionArms` — если точка села на самый конец оси, продолжения за
  ним нет. Удаление оси обязано звать `clearRoadIntersections(id)`, иначе
  закругление остаётся в сцене без оси, к которой было касательным.
  3. **Закругление идёт по КРОМКЕ проезжей части, а не по оси.** Ширина
     берётся из поперечника (`roadAxisWidthsFor`); у обычной полилинии её
     нет, там ширина 0 и дуги ложатся на сами оси. Угол узла — пересечение
     смещённых кромок (`intersectionCorner`), от него уже отступ по лучу.
     На осях без учёта ширины дуги слипаются в звёздочку вокруг точки
     пересечения — так и выглядела первая версия.
  4. **Контур покрытия — дуги ПЛЮС прямые кромки там, где ветви
     коллинеарны.** Покрытие строится веером из точки пересечения, а веер
     верен только если точка ВНУТРИ контура. У примыкания закруглений два,
     обе дуги лежат по одну сторону, и без прямой кромки сквозной дороги
     узел оказывается снаружи — веер выворачивается. ⚠️ На полилиниях
     нулевой ширины это НЕ ловится: замыкающая хорда проходит ровно через
     узел, и «внутри/снаружи» вырождается (проверено — тест проходил и со
     сломанным контуром). В `test-intersections` для этого отдельная
     фикстура примыкания на осях с шириной.
  Уширение (`flare`) сдвигает кромку у узла, отгон (`taper`) сводит её
  обратно к обычной ширине — это и есть разгонная полоса в плане, не
  отдельная сущность. Площадь покрытия в тесте считается ИЗ геометрии
  (плюс шириной 2·w до устьев плюс четыре сегмента R²(1 − π/4)), а не
  числом: сошлась 1244.7 против 1243.4 м² при 20 сегментах на дугу.
  5. **Вылет устья меряется ОТ УЗЛА вдоль оси, а не от угла кромок.** Угол
     отодвинут от узла на полуширину поперечной дороги, поэтому
     `tangentDist` короче настоящего вылета ровно на неё (в тесте 20 против
     25 при w=5, R=20). По этому числу коридор обрывается — с ошибкой под
     покрытием остался бы кусок коридора. Считается как проекция точки
     касания на направление ветви (`alongA`/`alongB`).
  6. **Коридор обрывается у узла через тот же `skipInterval`, что и на
     острых углах.** `corridorLoftPush` по этому массиву САМ ставит торцы на
     границах пропуска, поэтому отдельный код закрытия конца не нужен.
     Пикеты внутри узла выбрасываются, а на границы устья ставятся ровно
     (`applyNodeGapsToStations`) — иначе торец встанет на ближайший
     случайный пикет, а не заподлицо с покрытием. Создание, правка и снятие
     узла обязаны звать `syncCorridorsForIntersection` (и боевой путь, и
     отладочный `BimLvaDebug.buildIntersection` — на этом уже попадался:
     тест показывал, что пикеты внутри узла остались).
  7. **Одежда под узлом берётся от оси с БОЛЕЕ МОЩНОЙ конструкцией**, а не
     «от первой, у которой слои есть»: последнее зависит от порядка выбора
     осей в диалоге, и добавленный во вторую ось слой просто не попадал под
     узел. Толщина слоя снимается на оси (`off ≈ 0`) — у кромки слои
     обрываются иначе, а полотно под узлом одно на все направления.
  Выгрузка: DXF — слой «Узел», каждый слой одежды своим `3DSOLID` плюс
  замкнутый контур; LandXML — только ВЕРХ покрытия поверхностью (Surface
  это поверхность, а не тело; сложить слои в один TIN значило бы отдать
  Civil самопересекающийся набор граней).
  8. **Бордюр/обочина протягиваются по скруглениям.** Покрытие узла кончается
     на кромке проезжей части, коридор обрезан у устья — без протяжки у
     устьев зияют разрывы (владелец их и увидел). `nodeOuterProfile` берёт
     точки шаблона за кромкой и пересчитывает их ОТ КРОМКИ (`off − edgeOff`,
     `dz − dzEdge`): контур узла уже несёт свою высоту, абсолютные dz
     наложились бы вторым слоем. Тянется по дугам и прямым кромкам, но НЕ
     через устья ветвей — там дорога продолжается и бордюр даёт коридор,
     поэтому контур режется на участки (`runs`). Берётся правая сторона
     шаблона (обход контура против часовой, наружу смотрит правая нормаль);
     у несимметричного шаблона левая по кольцу не воспроизводится — у кольца
     нет «левой» стороны дороги. ⚠️ Проверять это на шаблоне ПО УМОЛЧАНИЮ
     бесполезно: за кромкой там пусто, вылет 0, и «протяжка есть» — правда
     при нулевой геометрии. В тесте применяется пресет `curb`.
  9. **Отметка узла хранится ЦЕЛЕВЫМ значением (`rec.zTarget`), а НЕ сдвигом.**
     Сдвиг работал, пока отметка никуда не запекалась. Как только узел стал
     править профиль подходящих осей, расчётная отметка сама стала равна
     целевой — и сдвиг прибавлялся к ней на КАЖДОМ пересчёте: узел уезжал
     вверх от любой правки радиуса. С целевым значением поправка
     `zTarget − crossPoint.z` сходится к нулю, и пересчёт идемпотентен.
     Закреплено проверкой «отметка не ползёт от повторных пересчётов»
     (три холостых `editIntersection`) — на эмуляции прежней семантики она
     даёт 1619.15 вместо 1613.15.
  8a. **Ширина узла — по ПРОЕЗЖЕЙ ЧАСТИ (точки L/R), а не по габариту
     шаблона.** `model.widthL/R` считаются по крайним точкам и включают
     бордюр, обочину, кювет: кромка узла уходила за кромку дороги (5.15
     против 5.00 у шаблона «С бордюром»), и на устье получалась ступенька —
     бордюр узла вставал на 15 см наружу от бордюра дороги. Внешний профиль
     отсчитывается от той же кромки (`templatePavementWidths`), поэтому они
     теперь продолжают друг друга без стыка.
  8b. **Узлы строятся сами при пересечении осей** (`autoBuildNodesFor`,
     галочка «Строить узлы сразу», умолчание — включено, живёт в
     localStorage). Только для `role === 'road-axis'`: обычные полилинии
     (бровки, контуры, линии выхода откосов) пересекаются сплошь и рядом.
     Тип определяется сам: конец оси на чужой оси → примыкание, иначе крест.
     ⚠️ В `npm run smoke` автопостроение НАМЕРЕННО выключено: оси-фикстуры
     там лежат в паре метров друг от друга, узел обрезал бы коридор у устья,
     и станция на PI исчезала бы из выборки — две проверки поперечников
     падали именно так. Само автопостроение закрыто в `test-intersections`.
  9a. **Заданную отметку ПРИСВАИВАТЬ, а не прибавлять сдвигом.** `outline` и
     `arcs` держат ОДНИ И ТЕ ЖЕ объекты точек (контур собран из точек дуг),
     и два прохода со сложением сдвигали дуги ДВАЖДЫ: при целевой отметке 5
     контур уезжал на 5…10, покрытие выворачивалось чашей с задранными
     краями — ровно то, что владелец увидел при перетаскивании ручки.
     Присваивание идемпотентно и не зависит от того, успел ли профиль оси
     перенять отметку. ⚠️ На пути «через ручку» это НЕ ловится: там отметка
     запекается в ось, поправка становится нулевой и ошибка прячется —
     в тесте расчёт дёргается напрямую с `zTarget`.
  9b. **В ось садятся ровно ДВЕ вершины — по одной на устье.** Вершину в
     самой точке пересечения ставить нельзя: обе соседние уже на отметке
     узла, участок между ними и так прямой, а третья точка добавляет перелом
     на ровном месте и лишнюю ручку на оси — у двух осей такие вершины ещё и
     совпадают в одной точке (владелец увидел два ярлыка отметки рядом).
     Промежуточная версия этой вершины к тому же не обновлялась при повторном
     подъёме и давала провал буквой V под покрытием (1602.1 против 1604.5);
     ⚠️ один шаг подъёма это не ловил — на первом все вершины ставятся заново
     и совпадают, поэтому в тесте подъём многошаговый. Свои вершины оси
     внутри узла не трогаем: это геометрия пользователя.
  9c. **Вершины, посаженные узлом, — ПРОИЗВОДНЫЕ, но это настоящие вершины
     оси, и они держат её форму.** Пока они на месте, ось идёт через прежнюю
     точку пересечения: потянул конец трассы — ось получает излом на старом
     узле, а сам узел «не замечает» сдвига. На профиле это пила из случайных
     переломов (то, что владелец и увидел). Поэтому: (а) пересечение при
     пересчёте ищется по АВТОРСКОЙ геометрии — `poly.pts.filter(p =>
     !p.nodeAnchor)`; (б) перед пересчётом свои вершины СНИМАЮТСЯ, и узел
     сажает их заново на новые устья; (в) ручек у них нет вовсе
     (`rebuildPolylineHandles` их пропускает) — иначе устье можно увести
     мышью, и вылечить это правкой оси уже нельзя.
     Точка подключения — `renderPolylinesList()`: это общее место «полилиния
     изменилась насовсем», внутрь перетаскивания оно не заходит, поэтому
     коридоры не пересобираются на каждый кадр. Защита от рекурсии —
     флаг `resyncingNodes` (`refreshRoadIntersection` зовёт список обратно).
  9d. **Якорь нельзя двигать на месте — только снять и поставить заново.**
     Он сам вершина оси, и сдвиг деформирует линию, по которой считается
     пикетаж: вершина промахивается мимо нового устья (замерено ПК 65.8 при
     устье 82.5, а второй якорь садился на конец трассы). Снятая вершина
     лежала НА линии, поэтому удаление форму не меняет и вставка по пикету
     попадает точно (осталось 0.04 м от проекции на звено).
     И ещё: узел и профиль зависят друг от друга (посадка вершин меняет
     пикетаж, от которого считались устья), поэтому `refreshRoadIntersection`
     крутит «посадить → пересчитать» ДО СХОЖДЕНИЯ, а не один раз.
     ⚠️ В тесте двигать вершину по индексу 1 нельзя: у оси с узлом там сидит
     служебная вершина, и «сдвиг вершины 1» согнёт ось вместо переноса —
     концы искать по краям профиля.
  9k. **Ручки переносятся кликами, а не зажатой кнопкой** (`runGrabHandle`,
     2026-08-20, просьба владельца): нажал — взял, довёл, нажал — положил, как
     гриппы в AutoCAD. Esc возвращает на место.
     * Перетаскивание с ЗАЖАТОЙ кнопкой оставлено рабочим: на нём держатся уже
       написанные проверки (smoke двигает вершины и ручку узла именно так), да
       и привычка у части пользователей та же. Различаются они по сдвигу:
       ушёл дальше `GRAB_CLICK_PX` (4 px) до отпускания — это перетаскивание и
       оно завершается на `pointerup`; не ушёл — ручка остаётся «на руках».
     * Зачем: с зажатой кнопкой курсор дрожит на отпускании, и привязка
       срабатывает в последний момент не туда. Отпущенная кнопка позволяет
       навести на нужную точку и подтвердить кликом.
     * Состояние «на руках» видно: `.is-carry` — пунктирная обводка. Без
       отметки его не отличить от наведения, и ручка «залипала» бы молча.
     * Отмена по Esc обязана ВЕРНУТЬ исходное положение (у вершины — копия
       точки, снятая на нажатии; у узла — прежняя отметка), иначе взятую
       ручку некуда деть, кроме как поставить куда попало.

  9j. **Привязка к ЧУЖОЙ оси при черчении новой** (`snapToRoadAxis`,
     2026-08-20) — подвёл ось к оси, точка села ровно на неё, получился
     Т-образный узел (`autoBuildNodesFor` видит конец оси на чужой оси).
     * ⚠️ Обычная привязка сюда НЕ ГОДИТСЯ: ось нарисована `Line2`, у которой
       нет атрибута `position` (позиции в `instanceStart/End`), и
       `snapPrimitiveOf` по ней возвращает пусто. Поэтому своя — по
       спроецированным точкам записи, тем же приёмом, что и пикинг по линии.
     * Порог в ПИКСЕЛЯХ (`ROAD_AXIS_SNAP_PX` = 14), не в метрах: в метрах он
       либо не ловит на общем виде, либо липнет ко всему при зуме.
     * Точка берётся НА звене (проекция курсора), а не ближайшая вершина: узел
       ставится там, где подвели ось.
     * Приоритет выше геометрии модели: подводя ось к оси, целятся в неё.
     ⚠️ В тесте целиться надо в СПРОЕЦИРОВАННУЮ точку оси
     (`polylineScreenPts`), и обязательна встречная проверка «вдали от оси
     привязка молчит» — иначе привязка, хватающая всё подряд, прошла бы.
     Замерено: отход от оси 0.0000 м при попадании 8.8 px.

  9e. **Примыкание «впритык»: ось не обязана дотягиваться до чужой оси.**
     На практике конец примыкающей дороги привязывают к КРОМКЕ главной —
     строгого пересечения нет, и узел не строился вовсе. `findAxisTouch`
     ловит это по концам осей с допуском «сумма полуширин, но не меньше
     метра». ⚠️ Очищенную от служебных вершин копию оси делать голым
     `{ pts }` НЕЛЬЗЯ: от `role` зависит ширина, от неё — допуск; с голым
     объектом ширина падала в ноль и живой узел сносило при первой же
     правке соседней оси.
  9f. **Подписи углов в сцене** (`.node-corner`, «R 15 · 90°», клик — задать
     радиус) живут в том же слое, что ручка узла, и пересобираются в
     `refreshRoadIntersection`: ждать кадра нельзя, иначе после правки на
     экране остаётся прежний радиус.
  9h. **Бровки дороги и узла СШИТЫ в одну линию** (2026-08-20, просьба
     владельца «объединить выходы на рельеф»): плечо → дуга узла → плечо, и
     откос по ней один. Раньше на каждый стык приходились ДВЕ поверхности:
     между ними оставался шов, а на вогнутом углу устья — перехлёст
     («бабочка» со скриншота). Сплошная линия лечит это сама — в углу, где
     соседние точки бровки совпадают, построитель уже ставит веер
     (`dist < 1e-6`), второй механизм не нужен.
     * Владелец цепочки — САМ УЗЕЛ, а не ось: она идёт через ДВЕ оси, и
       приписать её одной нельзя. Дорожные куски остаются своими записями
       (их убирает дорожный проход), просто своего откоса не получают:
       `browTouchesAny` → `removeSlopeModelsForPolyline` и `sm: null`.
     * Разворот куска считается ГЕОМЕТРИЧЕСКИ, а сторона проверяется:
       наружу обязана смотреть ПРАВАЯ нормаль (как у контура узла), то есть
       годится правая бровка вперёд или левая назад. Не сошлось — кусок не
       берём: иначе откос вывернется внутрь, а объём останется правдоподобным
       (см. предупреждение про `outwardMin` ниже).
     * Совпавшую точку в стыке НЕ дублируем: два одинаковых узла подряд
       вырождают веер.
     ⚠️ Проверять надо ЧИСЛО поверхностей, а не стык: концы линий выхода
     сходились в 0.000 м и ДО сшивки — шов был не разрывом, а ПЕРЕХЛЁСТОМ.
     Замерено на кресте: поверхностей 12 → 4, линий выхода 12 → 4, вершин в
     них 123 → 96, насыпь 4869.8 → 4956.0 м³ (+1.8% — это и есть клин,
     который раньше не закрывался), время 244 → 264 мс.
  9i. **Перехлёст откоса («бабочка»): ЧТО ИЗМЕРЕНО и почему подрезки нет.**
     Инструмент — `BimLvaDebug.slopeFoldStats()`: самопересечения СЫРОЙ линии
     выхода, число подрезанных лучей, худшая петля.
     * ⚠️ Мерить перехлёст по ПРОРЕЖЕННОЙ линии нельзя: петли там появляются и
       исчезают от самого прореживания. Первый заход дал «44 самопересечения»
       — артефакт `simplifyPolylinePts`, а не геометрия.
     * Замерено на кресте (рельеф 400 коробок): **одна ось без узла — 0
       пересечений, крест с узлом — 80**. То есть их порождает узел. Но
       масштаб НЕ ТОТ: вынос откоса там 0.15 м (внешний профиль узла), а
       выходы расходятся на 0.4–0.5 м. Это БОКОВОЕ дрожание линии выхода, а
       не складка вдоль лучей.
     * ⚠️ Подрезка «луч обрезается там, где встречает соседний» БЫЛА НАПИСАНА
       И УБРАНА. Счётчик внутри функции показал: находит 228 пересечений,
       применяет НОЛЬ — точка пересечения лежит ЗА концом луча (проекция ≥ 1),
       потому что звенья линии выхода длиннее самих лучей. До счётчика четыре
       прогона подряд дали побайтно одинаковые числа, и это был единственный
       признак, что правится не то место.
     * ⚠️ Ещё одна ловушка того же дня: `D.slopes` собирает СВОЮ проекцию
       записи, и добавленное поле в неё не попадает — «подрезок 0» читалось
       из несуществующего поля. Та же семья, что с `edgeLeftPts`.
     * Для перехода насыпь↔выемка у `makeGeoIfc` появился параметр `tilt`:
       на плоской площадке ось либо везде выше земли, либо везде ниже, и стык
       двух режимов не воспроизводится вовсе.
     **Открыто:** крупная «бабочка» со скриншота владельца на фикстуре НЕ
     воспроизводится. Прежде чем писать подрезку заново — нужен его случай
     (файл или параметры оси и пресета).

  9g. **Откосы узла до рельефа** (`buildNodeSlopes`, `syncNodeSlopes`,
     2026-08-19) — ТОЙ ЖЕ машинкой, что у дороги: бровка это обычная скрытая
     полилиния `role='road-slope-brow'` (помечена `nodeIxId`/`nodeRunIndex`),
     тело считает `buildSlopeToTerrain`. Своего расчёта откоса заводить
     нельзя: линия выхода узла обязана стыковаться с линией выхода дороги, а
     две реализации разойдутся.
     * Бровка — НАРУЖНЫЙ край обстройки узла (самая дальняя точка того же
       внешнего профиля, что тянется по контуру), а не кромка проезжей части.
       Замерено на пресете `curb`: вынос 0.15 м.
     * Строится по УЧАСТКАМ контура (`runs`), а не по кольцу: в устьях дорога
       продолжается, и откос там даёт её коридор. Замкнуть кольцо значило бы
       перегородить откосом саму дорогу. У креста участков 4.
     * **Кнопок и галочек для откосов больше нет вовсе** (просьба владельца,
       2026-08-19): ни `#roadXsSlopeOn`, ни `#roadXsSlope`. Откосы строятся
       ВСЕГДА вместе с полотном — и у дороги, и у узла (`nodeSlopesWanted`
       теперь проверяет только наличие поперечников у подходящей оси).
       У оси дороги «△ Откосы» в списке полилиний и в контекстном меню
       скрыта. На ОБЫЧНОЙ полилинии кнопка осталась намеренно: строить откос
       от каждой начерченной линии по умолчанию нельзя — это и осевые, и
       контуры, и сами линии выхода откосов.
     * Смена шаблона поперечника обязана пересчитывать узел
       (`refreshNodesOnPolyline` в `applyRoadTemplateChange`): от шаблона
       зависят ширина кромки, внешний профиль и слои одежды. Без этого
       переключение на «с бордюром» оставляло у узла `outer = null`, и откос
       начинался прямо от проезжей части (замерено: вынос 0 вместо 0.15).
     * ⚠️ Пересчёт откосов **отложен на отпускание ручки** отметки:
       `refreshRoadIntersection` зовётся на КАЖДЫЙ pointermove, а откос — это
       выборка рельефа лучами с шагом 0.5 м вокруг всего контура.
     ⚠️ **Проверять только на СПЛОШНОМ рельефе.** `IFCRECTANGLEPROFILEDEF`
     задаёт ПОЛНЫЕ размеры, поэтому фикстура `makeGeoIfc` с `step: 6` даёт
     коробки 3×3 с дырами между ними. Луч откоса проваливается в дыру,
     проходит мимо правильной точки выхода и цепляется за землю дальше:
     замерено 208 сечений из 312 с заложением 1.5…5.56 при заданном 1:1.5 —
     и это артефакт фикстуры, а не код. При `step: 3` коробки смыкаются, и
     заложение держится ровно 1.500 во всех 320 сечениях.
     ⚠️ И оси в тесте класть надо в ЦЕНТР рельефа (`modelBounds.centerX/Y`), а
     не в ноль сцены: второй файл в сводке зовёт до-центрирование, слой земли
     стоит уже не у нуля, и половина сечений уходит за её край (замерено 164
     «без земли» из 320 — проверка заложения считалась бы по огрызку).
     Самая опасная ошибка тут — знак нормали: внутрь откос закрыл бы сам узел,
     а объём остался бы правдоподобным. Поэтому в `BimLvaDebug.nodeSlopes()`
     есть `outwardMin` (прирост радиуса от бровки к выходу) и `layOff`
     (сколько сечений мимо заложения 1:m) — проверяется числом, а не глазами.
     ⚠️ **Отладочный `BimLvaDebug.buildIntersection` не убирал прежний узел на
     той же паре осей**, хотя боевой путь это делает. С включённым
     автопостроением узел уже стоял, и на паре оказывалось ДВА: их бровки-откосы
     копились (замерено 60 вместо 4) и шли в расчёт как «земля» — насыпь падала
     с 618 до 38 м³, `outwardMin` до нуля, стык 10.3 м вместо 0.006. Искал это
     долго, потому что чинил похожие места (воскрешение откосов снятому узлу,
     разрозненную уборку) — а счётчик не двигался. Нашлось только пошаговой
     трассировкой прямо в тесте: «оси созданы: узлов живых 1 → узел построен:
     узлов живых 2». **Отладочный вход обязан вести себя как диалог**; если
     заводите новый — сверяйте его с боевым путём целиком, а не по главному
     действию.
     ⚠️ **Откосы на осях дороги НЕ строятся при первой сборке поперечников —
     открытая задача.** Просьба владельца «откосы всегда, без кнопок» выполнена
     наполовину: на узле строятся сами, на оси — при правке шаблона и по
     «Построить», но не при первой сборке. Безусловный вызов
     `buildRoadTemplateSlopes` в `buildRoadCrossSections` ломает окно
     поперечника: smoke даёт «ПКМ не сдвинул вид» и объём 0.713 вместо 1.125.
     **Четыре версии причины проверены и ОТБРОШЕНЫ**, числа во всех прогонах
     побайтно одинаковы (0.7128987109147633) — то есть менялось не то место:
       1. перерисовка окна изнутри сборки — то же самое и с флагом `quiet`;
       2. отложенный `scheduleRoadXsRebuild` — опровергнут чтением кода: для
          бровки он выходит сразу, у неё нет модели поперечников;
       3. чужая поверхность в выборке земли (`makeSlopeGroundSampler` считает
          готовые откосы проектной землёй) — снятие ВСЕХ прежних откосов до
          построения ничего не изменило;
       4. перехват активной оси внутренней пересборкой — сохранение
          `roadXsActive` в `rebuildRoadXsForPolyline` тоже ничего не изменило.
     Что известно точно, замерено: слева 0.462 м³, справа 0.251 м³, у обеих
     сторон по 10 граней TIN. Обе занижены, но ПО-РАЗНОМУ — значит причина
     несимметричная, и заложение/вылет/рельеф ни при чём.
     Следующий шаг: не выдвигать пятую гипотезу, а напечатать сами станции и
     точки бровки с авто-сборкой и без неё и сравнить напрямую. Приём уже
     сработал дважды в этой же задаче (счётчик бровок дал «узлов живых 2»,
     разбивка по сторонам дала несимметричность).
     ⚠️ **Автопостроение узлов не должно срабатывать на ВНУТРЕННИХ пересборках.**
     Откосы заводят полилинии-бровки → те дёргают список полилиний → `resync` →
     и на каждом витке каскада `autoBuildNodesFor` мог родить ещё один узел на
     той же паре осей. `hasNodeForPair` не спасает: новый узел успевает
     появиться раньше, чем предыдущий встанет в список. Замерено: 2 живых узла
     и 60 бровок вместо 4 — и они же попадали в расчёт как «земля», отчего
     насыпь падала с 618 до 38 м³. Лечится проверкой флагов в начале
     `autoBuildNodesFor` (`buildingRoadSlopes`, `syncingNodeSlopes`,
     `refreshingNodesOnPolyline`, `resyncingNodes`) — узлы строятся только по
     настоящей правке пользователя.
     ⚠️ **Снятие узла — только через `forgetIntersection`.** Путей снятия
     ЧЕТЫРЕ: замена узла на той же паре осей (`buildIntersection`), развод осей
     (`resyncNodesForPolyline`), кнопка в списке узлов и полная очистка. Каждый
     чистил своё: объекты сцены и запись убирали все, вершины-якоря — три,
     откосы — один. Осиротевшие бровки копились молча (за прогон теста 60
     вместо 4) и попадали в расчёт как «земля», отчего насыпь падала с 618 до
     38 м³, а `outwardMin` — до нуля. Теперь уборка одна на все четыре пути.
     ⚠️ **`syncCorridorsForIntersection` зовётся и для УЖЕ СНЯТОГО узла.**
     `clearRoadIntersections` вычёркивает узел и только потом просит пересобрать
     коридоры — чтобы дорога снова стала сплошной. Безусловный `syncNodeSlopes`
     там воскрешал откосы снятому узлу, и они оставались в сцене навсегда: за
     один прогон теста накопилось 60 бровок вместо 4, а вместе с ними — чужие
     площадки под ногами у расчёта (`makeSlopeGroundSampler` считает их землёй),
     отчего насыпь падала с 618 до 38 м³ и заложение уезжало. Поэтому:
     `if (roadIntersections.includes(rec)) syncNodeSlopes(rec); else dropNodeSlopes(rec.id)`.
     ⚠️ **Бровка дороги обязана РВАТЬСЯ там же, где полотно** — под узлом и на
     вывернутом сечении. Она строилась ОДНОЙ полилинией по всем пикетам сразу,
     включая разрыв: линия шла напрямую через перекрёсток, и откос по ней резал
     покрытие. Владелец это и увидел — чёрные клинья у устьев и зелёная линия
     поперёк узла. Разрывы считает `corridorBreakFlags`, ОДИН предикат на
     коридор и на бровку (`splitStationsAtBreaks`); вторая своя формула
     разошлась бы, и полотно рвалось бы в одном месте, а откос в другом.
     ⚠️ Проверять это ТОЛЬКО по вершинам бровки бесполезно: пикеты внутри узла
     и так вырезаны (`applyNodeGapsToStations`), внутрь попадал именно ОТРЕЗОК
     между ними — замерено 0 из 72 при сломанном коде. С серединами звеньев
     обратная подстановка даёт 4 из 140. Вторая метрика, ловящая то же самое
     наверняка, — расхождение концов бровок узла и дороги: 0.006 м после
     починки против 79.994 м до.
     ⚠️ Проверено обратной подстановкой (`side: 'right'` → `'left'`):
     `outwardMin` уходит с +1.82 на **−4.72**, а вот `layMin/layMax` остаются
     ровно 1.500 и `layOff` = 0. То есть **проверка заложения вывернутый откос
     НЕ ловит** — ловит только `outwardMin`. Убирать её из теста нельзя.
  10. **Подъём узла тянет за собой профили осей, но не концы трасс.**
     `syncAxisElevationsForNode` сажает в ось вершины на устьях узла и в
     самой точке пересечения с отметкой узла — участок от предыдущей вершины
     до устья становится уклоном. Правится САМ ПРОФИЛЬ, поэтому подъём виден
     и в окне профиля, а не только в 3D. Вершины помечаются
     (`nodeAnchor`/`nodeAnchorKey`), чтобы повторный подъём двигал прежние, а
     не плодил новые; удаление узла снимает их (`dropNodeAnchors`). После
     правки оси геометрия узла считается ЗАНОВО — устья могли сдвинуться
     вместе с профилем.
  11. **Контур узла обязан доходить до устья по ОБЕИМ кромкам ветви.** У двух
     соседних углов одной ветви отступы до касания РАЗНЫЕ: острый угол даёт
     длинный (`t = R/tg(φ/2)`), тупой — короткий. Устье берётся по большему
     (иначе коридор залезет под покрытие), и если вести контур прямо от точки
     касания одной дуги к точке касания соседней, между ними вырезается
     треугольник. Замерено на 45°: контур доходил до 10.4 м при устье 60.7 —
     **разрыв 50.3 м**, те самые «чёрные клинья» у устьев. Починка: каждый
     участок контура продлевается по прямой кромке до общего устья ветви
     (кромка → дуга → кромка), прямые вставки между участками — сами устья.
     ⚠️ На ПЕРПЕНДИКУЛЯРНЫХ осях это НЕ ловится: отступы у обоих углов равны,
     контур сам доходит до устья, и проверка зелёная при сломанном коде.
     В `test-intersections` для этого отдельная косая фикстура (45°).
     ⚠️ И мерить надо по КАЖДОЙ кромке отдельно: максимум по всей полосе
     ветви попадает в точку касания острого угла и разрыв на второй кромке
     не виден (на это уже потрачено время).
     Побочное следствие, не баг: на остром угле устье само по себе длинное
     (R=20 при 45° даёт 48 м отступа), и узел получается на сотню метров —
     это геометрия касательной дуги, а не ошибка; лечится радиусом.
  12. **Ручку узла нельзя поворачивать целиком.** `transform: rotate(45deg)`
     на контейнере наследуется подписью, и отметка встаёт наискось (так и
     было). Ромб рисует `::before` с поворотом, подпись `::after` остаётся
     горизонтальной; события ловит `::before` с `pointer-events: auto`.
  13. **У мешей коридора и узла `raycast` отключён намеренно**
     (`mesh.raycast = () => {}` в `makeRoadCorridorMesh`): это накладки, они
     не должны перехватывать выбор элементов модели. Поэтому обычный
     `intersectObjects` по ним возвращает пусто — свой пикинг
     (`pickRoadPart`) зовёт `THREE.Mesh.prototype.raycast.call(obj, …)`
     явно. На этом потеряно время: геометрия, габарит и луч были верны, а
     попаданий ноль. ⚠️ И целиться в тесте в ЦЕНТР ХОЛСТА бесполезно:
     «Вписать» кадрирует всю сцену вместе с моделью, в центре оказывается
     она. Целиться надо в спроецированные точки самого узла
     (`BimLvaDebug.nodeScreenPts`) — та же грабля, что с пикингом по линии.

- **Поперечники по оси — не полилинии.** Линии сечений живут в `roadXsGroup`,
  не в `drawnPolylines`: их десятки, это следствие оси. Правая нормаль в плане:
  касательная `(tx, ty)` → `(ty, −tx)`, смещение > 0 вправо по ходу. На
  переломе секущая — биссектриса правых нормалей входящего и исходящего
  (`miterRightFrame`), scale `1/cos(δ/2)` (cap 8), иначе кромки наезжают
  двумя перпендикулярами — Civil так и оставляет. Шаговые пикеты ближе
  `0.85·width·tan(δ/2)` к PI выкидываются. Промах земли — разрыв
  (`−Infinity`), не ноль, как на профиле. Пикеты: шаг плюс **вершины** оси
  (`pts`), не точки тесселяции дуги в `renderPts` — иначе потолок 200 станций
  съест конец трассы. Чертёж сечения не схлопывать по рельефу: min spanZ = 3 м,
  иначе на плоской площадке линия сливается с осью и окно выглядит пустым.
  Кромки ширины — сплошные (умолч. белые) на самой оси
  (`role === 'road-axis'`), в черновике пока тянешь; сама ось — пунктир.
  Цвет / толщина px / слой DXF оси и кромок правятся в списке полилиний
  и в окне поперечников (`Ось` / `Кромка`). Имена слоёв DXF по умолчанию —
  кириллица: Ось, Кромка, Поперечник, Откос, КДО, 2Д, 3Д, Точки, Тело.
  Файл DXF R2010 — UTF-8 (`$DWGCODEPAGE` остаётся ANSI_1251, как у AutoCAD).
  Окно поперечников открывается крупной кнопкой «⊟ Поперечники» на ленте: вкладка «Черчение»
  (своя панель «Сечение», не столбик под осью) и вкладка «Рельеф».
  Из окна профиля — та же кнопка внизу. «＋ слой» в окне поперечников
  наращивает одежду вниз от низа шаблона. «△ Откосы до рельефа» или
  галочка в форме — вместе с «Построить». Не только после Esc на оси.
  «Удалить все» полилинии
  обязано чистить и поперечники (`clearRoadXsModels`).
  «Построить» лофтит связи шаблона между станциями (`buildRoadCorridor`) —
  иначе на плоской площадке видны только засечки земли и кажется, что кнопка
  ничего не делает. Вырожденность грани — по длине 3D-нормали, не по `areaXY`:
  бока одежды и торцы сечения вертикальны, площадь в плане у них ноль, и
  формы становились открытыми листами. Подписи плана/профиля — HTML-оверлей
  (`#roadPlanAnnot` / `#polyProfileAnnot`), не SVG `<text>`: чертёж с
  `preserveAspectRatio="none"` растянул бы буквы. Шаблон не пересобирать связями «по смещению», если есть
  формы: у покрытия две точки на одном off (верх и низ). Пересборка линий
  сечения (`buildRoadXsLines`) не должна снимать полотно. Профиль оси —
  тот же `openPolylineProfile`, не второй движок. План, профиль и поперечник
  живут в одной немодальной палитре «План, профиль, поперечник» (`#roadXsModal`):
  план сверху, профиль под ним, поперечник справа — сразу, без вкладок.
  Зум колесом в каждом SVG; сдвиг вида — зажатый ПКМ (ЛКМ правит вершины
  и формы). Ручка `#rsSplitH` меняет высоту плана и профиля
  в пикселях (класс `rs-locked`), `#rsSplitProfileTable` — высоту таблицы
  профиля (`--rs-prof-table`, умолч. 136 px, не 72), `#rsSplitV` — ширину
  поперечника. Размер
  палитры и окна браузера чертежи по вертикали не тянут: иначе flex-grow
  раздувал все три вместе с `72vh`. Угол окна — `.rs-win-grip`.
  Шаблоны дороги в `#roadXsCatalog` + «Применить на ось».
  Шаг поперечников раздельный: `#roadXsStep` на прямых, `#roadXsStepCurve`
  на кривых (короткие хорды сопряжения с конечным R). Если передать только
  `step`, кривая берёт тот же шаг — старые вызовы не густеют.
  Фигуры (бордюр / кювет / …) на чертеже сечения **жёсткие**: тянем заливку —
  `detachShapeAnchors` клонирует общий якорь в состав фигуры, все её точки
  едут одним вектором; на отпускании `snapShapeToNearestPoint` сажает
  ближайшую вершину на ближайшую чужую точку (порог ~14 px). Не двигать
  только exclusive-точки, оставляя якорь: форма растягивается.
  Таскать, закреплять (лево/право/низ), сворачивать в лоток.
  Тот же хром у всех `.modal-backdrop.floating-panel` (`createFloatingPanel`).
  Поле `#roadXsLayerThk` меняет толщину верхнего слоя одежды у кромки
  (`setFirstLayerThickness`), не только добавляет новый. «＋ слой» по-прежнему
  наращивает одежду вниз. Откосы до земли от кромок шаблона —
  `buildRoadTemplateSlopes`: скрытые бровки `role=road-slope-brow` (не в
  списке полилиний) и тот же `buildSlopeToTerrain`. На чертеже сечения
  лучи `xs-slope` считаются тем же `computeSlopeCrossSection`, что TIN.
  Линия земли на чертеже (`xs-ground`) доснимается за ширину покрытия:
  до крайней видимой точки шаблона, а если откос вышел на рельеф — до
  смещения выхода (`roadXsGroundNeedRange` / `roadXsGroundSamples`), без
  пересъёмки полотна. Проверено в `npm run smoke`: земля не короче края
  бордюра и не короче выхода откоса.
  Чертёж сечения зумится как профиль: колесо к курсору (`zoomRoadXsAt`),
  Shift+колесо только по высоте, фон — пан по пиксельной дельте исходного
  кадра (не через `roadXsClientToOffZ` на каждом move — иначе кадр уезжает),
  ⤢ сбрасывает `roadXsView`. Готовые фигуры (`addTemplateFigure`) — бордюр /
  обочина / кювет / прямоугольник / трапеция / треугольник — к якорю наружу
  от оси, без `addTemplatePoint` (тот режет связи покрытия). Новые точки
  фигуры помнят родителя (`parent`, `relOff`/`relDz`): правило на якоре
  двигает весь узел. На точке `pt.rule`: `{ when, value, thenDz, thenOff,
  thenHide, elseDz, elseOff, elseHide }`; `resolveTemplatePoints` на каждой
  станции (`work>`/`work<`/`gAbove`/`gBelow`/`axis>`/`axis<`). Скрытый
  родитель прячет детей — коридор и заливка формы их не берут.

- **Удаление полилинии не по старому индексу.** `deleteDrawnPolyline` сначала
  зовёт `removeSlopeModelsForPolyline`, а та через `dropPoly` уже вынимает
  линию выхода из `drawnPolylines`. Индекс, снятый до этого, указывает на
  соседа: его вычёркивают из списка, объект в `drawGroup` остаётся — в
  таблице «полилиний нет», а контур на площадке виден. После dropPoly искать
  запись заново по id; в конце сверять детей `drawGroup` с записями
  (`purgeOrphanDrawObjects`). Повторное «Построить» по той же бровке
  заменяет старое построение, а не копит вторую площадку.

- **Вертикальная кривая ≠ радиус плана и ≠ «Верт. переход».** План живёт в
  `radii[]`, профиль — в `vRadii[]` той же длины, что `pts`. Класть
  вертикальный радиус в `radii` нельзя: сопряжение плана начнёт гнуть
  отметки. «Верт. переход» — стояки с одинаковым X/Y, это другое. На
  профиле ПКМ без сдвига открывает меню (сдвиг по-прежнему панорамирует);
  PVI остаётся кружком, дуга через него не идёт. 2D-полилинии вертикальную
  кривую не делают.
- **Панель профиля не лочить фиксированной высотой.** `rs-locked` фиксирует
  только `--rs-plan`. Профиль `flex: 1` забирает остаток карточки — иначе
  чертёж упирается в таблицу, а внизу окна пусто. Ручка таблицы делит уже
  выросшую панель. Smoke: при росте окна план стоит, профиль и поперечник
  растут.

## 10. Производительность вьювера — что измерено и что осталось

**НАЙДЕНО И ПОДТВЕРЖДЕНО ЗАМЕРОМ, НО ЕЩЁ НЕ ПОЧИНЕНО: механизм снижения
качества при вращении мёртв ровно на больших моделях.** Код на месте:
`controls.addEventListener('start')` роняет `setPixelRatio(1)`, а
`applyRenderQuality()` включает «тяжёлый» режим. Оба порога считают
`allMeshes.length`. Но батчинг (от `IFC_BATCH_THRESHOLD` = 2000 фрагментов)
склеивает модель в считанные меши: замер на сетке **20 000 элементов дал
`allMeshes.length === 1`**, то есть

- `allMeshes.length > 8000` (снижение при вращении) — НЕ срабатывает;
- `allMeshes.length > 12000` (`applyRenderQuality`) — НЕ срабатывает;
- `allMeshes.length > 15000` (отключение зума к курсору) — НЕ срабатывает.

На 4K-экране крупная модель крутится на полной пиксельной плотности — вчетверо
больше работы, чем задумано. Спасает только авто-`perfMode` от трёх файлов в
сводке (`ifcCount >= 3`); один большой файл под него не попадает.
Починка (по убыванию отдачи, владелец пока не давал добро):
1. считать тяжесть по треугольникам или `totalElements`, а не по объектам сцены —
   это оживит уже написанный код;
2. не гонять DOM каждый кадр: `updatePolylineHandles`,
   `updatePolylineAnnotations`, метки и подписи координат проецируются
   **безусловно на каждом кадре**, даже когда сцена не перерисовывается
   (`sceneNeedsRender` их не прикрывает);
3. сильнее ронять разрешение на время движения с восстановлением через ~150 мс.

⚠️ FPS в песочнице мерить бесполезно: headless-Chromium рисует программно
(SwiftShader), без GPU. Числа «стало X кадров» оттуда брать нельзя.

**Счётчик памяти в статус-баре** (`#memReadout`, справа от FPS): «ОЗУ N МБ ·
модели M МБ». Грабли, на которые уже наступил:
- `performance.memory` — **только Chrome**, и он сознательно огрубляет числа
  (защита от side-channel). Точными их считать нельзя, годятся для «до и
  после». В других браузерах показываем один свой счёт моделей, а не ноль.
- **Видеопамять сюда не входит вовсе** — браузер её не отдаёт. То есть
  «модели M МБ» это буферы в куче JS, а не то, что уехало в GPU.
- Вес моделей считается ОДИН раз при загрузке (`modData.geometryBytes`).
  Обходить фрагменты на каждое обновление счётчика нельзя: на файле АР это
  730 000 итераций дважды в секунду — счётчик стоил бы дороже, чем показывает.
  Батч держит свою склеенную копию вершин рядом с исходными фрагментами,
  отсюда ×2 у батченых моделей.
- Целые мегабайты врали на мелких моделях («0 МБ» при 0.4 МБ) и счётчик
  выглядел сломанным — до 10 МБ печатаем десятую долю.

**Про GPU.** Отрисовка УЖЕ на GPU — three.js через WebGL2, иначе 700 000
элементов не крутились бы вовсе. На CPU и в один поток остальное: разбор STEP
и тесселяция в web-ifc (WASM), построение BVH, батчинг. Поэтому «прикрутить
GPU» к загрузке нечего — там нечего распараллеливать на шейдерах. Реальные
пути ускорения загрузки: (а) кэш геометрии — сделан, §кэш ниже; (б)
**`web-ifc-mt` (многопоточный WASM) уже вендорится** (`web-ifc-mt.wasm`,
`web-ifc-mt.worker.js` в `tools/vendor.mjs`), но вьювер его НЕ использует —
это неиспользованный запас, требует COOP/COEP-заголовков, а их на GitHub Pages
не поставить; (в) WebGPU-рендерер three — это про отрисовку, не про загрузку.

### Грабли оформления

- **Кнопки ленты «разъезжались» по высоте — замерено, не на глаз.** На одной
  вкладке «Черчение» было ТРИ высоты крупных кнопок: 56 / 70 / 74 px (подпись
  в одну строку против двух, символьная иконка против рисованной), на «Файле»
  67 против 72 у остальных. Лечится не подгонкой надписей, а ФИКСИРОВАННЫМИ
  слотами: иконке `height: 22px` во флексе, подписи `-webkit-line-clamp: 2`
  и `min-height: 2.3em` — две строки всегда, даже если надпись одна.
  ⚠️ `min-height` на голом `.rbtn-big` НЕ РАБОТАЕТ: выше стоит
  `.top .rpanel .btn { min-height: 0 }` — три класса против одного, и правило
  молча проигрывает. Нужен селектор не слабее.
  ⚠️ Кнопка «Локально» — это `<label>`, её ловит отдельное
  `.top .rpanel label.btn { min-height: 0 }`. Без варианта с элементом
  (`label.rbtn-big`) она одна остаётся на 67 px, и вкладка «Файл» отличается
  от всех.
- **Главная кнопка окна — всегда крайняя справа, правилом в CSS.** Замерено:
  из двух с лишним десятков немодальных окон в трёх она стояла ПЕРВОЙ.
  `.modal-actions > * { order: 1 }` плюс `order: 2` у `.load-btn`/`.btn-cloud`
  дешевле и надёжнее, чем переставлять кнопки в двадцати местах разметки —
  там легко пропустить окно и снова получить разнобой.
  ⚠️ **Проверять порядок положением на экране НЕЛЬЗЯ**: окна закрыты
  (`display:none`), и `getBoundingClientRect` у всех даёт нули — сортировка
  «по экрану» метит окна наугад. Так проверка и соврала на четырёх окнах при
  ВЕРНОМ CSS. Считать надо как flexbox: сначала `order`, при равенстве —
  порядок в разметке.

- **`[data-tip]` перебивает `position: absolute` у накладок над сценой.**
  Правило-якорь подсказки `[data-tip] { position: relative }` живёт в стилях
  НИЖЕ, чем классы накладок, а специфичность у них одинаковая (0,1,0) — значит
  выигрывает оно. Подпись угла узла `.node-corner` из-за этого становилась
  relative-блоком в потоке и растягивалась во всю ширину слоя: на экране —
  полоса до края окна (владелец: «строка растянулась в бесконечность»).
  Замерено: 864 px вместо 78 px, `position: relative`, `offsetParent = #stage`.
  Починка — поднять специфичность (`#node-handles .node-corner`), а не убирать
  `data-tip`. **Любой новой абсолютно позиционированной накладке с `data-tip`
  грозит то же самое.** Проверять не глазами, а `getBoundingClientRect()` +
  `getComputedStyle().position`.
- **Слою накладок нужны СВОИ правила.** У `#node-handles` их не было вовсе, и
  он был обычным блоком в потоке: 846×51 в верхней части сцены с
  `pointer-events: auto`, то есть ещё и перехватывал клики по модели в этой
  полосе, а подписи ехали на 9 px мимо холста (origin не совпадал с
  `projectToPixels`). Образец — `#polyline-handles`:
  `position:absolute; inset:0; pointer-events:none; z-index; overflow:hidden`.
  Заводя новый слой (`<div id=…>` рядом с `#polyline-annot`), сразу копировать
  этот блок правил.
- **`margin-left: auto` не работает вместе с `overflow-x: auto`.** Правая
  группа ленты (тема, кабинет) уезжала за край экрана. Лечится тем, что
  прокручивается ТОЛЬКО середина, а правая группа закреплена отдельным
  флекс-элементом.
- **Полностраничный скриншот в headless-Chromium ВРЁТ** там, где полупрозрачный
  DOM лежит поверх WebGL-холста: видовой куб и тосты выглядели белыми в тёмной
  теме, хотя `getComputedStyle` давал `rgb(24,29,37)`. Проверять надо
  вычисленным стилем и снимком ЭЛЕМЕНТА (`locator.screenshot()`), а не общей
  картинкой. На это потрачено время дважды.
- **Тему ставить крошечным скриптом в `<head>`**, до отрисовки — иначе страница
  мигает светлой. И `applyTheme` не должен трогать `bgThemes`/`grid`: они
  объявлены ниже по модулю, обращение оттуда — TDZ, роняющий весь скрипт
  (та же семья, что с `esc`/`escAttr`). Связывание темы с холстом
  регистрируется ПОСЛЕ объявлений, через `onThemeChanged`.
- **Фон 3D-холста в CSS-токенах не участвует** — это WebGL. Для него свой набор
  (`bgThemes` / `bgThemesDark`) и `applySceneBackground()`.
- Белый цвет надо разбирать ПО СВОЙСТВУ: `background: #fff` — это поверхность,
  а `color: #fff` на залитой кнопке — отдельный токен `--on-fill`, который в
  тёмной теме НЕ инвертируется. Слепая замена сломала бы кнопки.
- Полупрозрачные накладки поверх холста — токен `--glass`; жёсткий
  `rgba(255,255,255,…)` светился в тёмной теме.
- Подписи в кубе видов не влезали в 30 px; «Персп» из куба убран вовсе —
  проекция переключается в ленте, дублировать её значит лишнее движение.
- Двухрядная лента: три мелкие кнопки столбиком плюс подпись группы требуют
  88 px, в 74 подписи обрезаются.
- Боковые панели конкурента — плиты встык со сценой, угол 0. Не повторять
  ни это, ни рейку слева. Зазор палитры — к хрому приложения (`--bg`), не
  оверлей на WebGL. 6 px на полном окне не читался, стоит 10 px. Сцена
  вписана в ту же рамку, иначе палитры снова читаются как стены проёма.
  Откреплённая панель тоже с `--r` и `--line`, без тени и без оранжевой
  рамки (оранжевый — выделение в сцене). Кнопка «Поиск по параметру» без
  своих стилей в тёмной теме становится системным белым прямоугольником.

## 14. Форматы экспорта — DXF, LandXML, STEP, DWG

**Состояние (2026-08-17):** DXF требовал трёх критических исправлений (BYBLOCK, BYLAYER, субклассы Polyline/Vertex/SequenceEnd). Вместо добавления всё новых патчей выбран стратегический ход: поддержка трёх универсальных форматов.

### Реализованные форматы

**DXF (R2010, AC1024, UTF-8)**
- ✅ Полилинии (POLYLINE с вершинами, поддержка bulge для дуг)
- ✅ Точки координат (POINT)
- ✅ Поверхности (3DSOLID в формате ACIS SAT 700)
- ✅ Экспорт полилиний (с поперечниками и откосами)
- ⚠️ Требовал трёх фиксов структуры (коммиты 59cf5d7, dd14cae, e5fdb29, 40f3edf)

**LandXML 1.2 (XML-текст)**
- ✅ Поверхности (Surface → TIN с Pnts/Faces, координаты N/E/Z)
- ✅ Полилинии (Alignment → CoordGeom для линий и дуг, PntList для точек)
- ✅ Совместимость: Civil 3D 2018+ (Import LandXML)
- ✅ Координаты: мировые, метры, комплексные E/N/Z
- 📝 Генерируется чистым строк-кодом, отладка в текстовом редакторе

### Добавляются (2026-08-17+)

**STEP (ISO 10303-21, `.stp`/`.step`)**
- Библиотека: `occt-wasm@4.3.0` (OpenCascade, MIT/Apache-2.0)
- WebAssembly, ~4-5 МБ
- Универсален для 3D (CAD, CAM, FEA)
- Точность: double, хорош для координат
- Кнопка ⤓ STEP в Черчение и Откосы

**DWG (Autodesk, native binary format)**
- Библиотека: `@node-projects/acad-ts@2.4.2` (MIT, open-source TypeScript)
- WebAssembly + JavaScript
- Форматы: DWG 2000/2004/2007/2010/2013/2018
- Замена DXF для пользователей AutoCAD
- Кнопка ⤓ DWG рядом с DXF

|--------|-------------|-----------|-------|-----------|----------|---------|
| **DXF** | ✅ 3DSOLID | ✅ POLYLINE | ✅ | Абсолютные, м | 2010+ | — |
| **LandXML** | ✅ Surface TIN | ✅ Alignment | ✅ BreakLine | N/E/Z, м | 2018+ | — |

### Примечания

- **DXF против DWG:** DXF — текстовый (R2010), DWG — двоичный (native). DWG надёжнее для сложной геометрии, DXF универсален.
- **LandXML:** Специализирован для гражданского проектирования (дороги, поверхности, рельеф). Лучший выбор для Civil 3D.
- **STEP:** Промышленный стандарт. Полезен для моделей, которые будут открыты в FEA, CAM, PLM-системах.
- **Координаты:** Все форматы экспортируют мировые абсолютные координаты (не относительно сцены). Метры во всех случаях.
